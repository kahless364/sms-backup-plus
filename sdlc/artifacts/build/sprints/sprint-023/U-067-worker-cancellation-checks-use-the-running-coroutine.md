# U-067: Make the Backup and Restore Workers' Three Cancellation Checks Observe the Running Job, and Prove Each One With a Test That Cancels the Work Mid-Loop

## Story
As the owner of this private, unpublished SMS Backup+ build (its only user, who presses the cancel button on a running backup or restore),
I want the backup loop and both restore loops to stop at the start of their next pass once the work is cancelled, by the check each loop already contains for that purpose,
So that stopping does not depend on the library's progress call happening to notice the cancellation (under test it never does; in production it does only when the call really suspends), and so that the Kotlin, coroutines and WorkManager upgrades of design DES-MODERNIZATION-014 (S2, S4) have a cancellation test as their stop rule instead of a compiler warning.

Source: bug BUG-022 (`sdlc/artifacts/stories/BUG-022-worker-cancellation-checks-do-nothing.md`, status ready, severity low, priority medium), with its Solution Architect Suggested Approach (option 1, `currentCoroutineContext().ensureActive()`). The story fixes exactly that bug and nothing beside it. Placement is ruled by the orchestrator (Record 13 row 11 and Record 14 row 11, decision appendix of `sdlc/artifacts/build/feasibility/U-062/thunderbird-mail-libraries-feasibility-analysis.md`): "As its own small story, after story U-066 closes and before the toolchain story". There is no REQ-* source; the behaviour the story restores is already stated by the scheduler contract (CNTR-MODERNIZATION-004 rule 7, `:279`) and by DES-MODERNIZATION-005 (`:215-218`).

What is wrong, in short. In `BackupWorker.kt` (`:331`) and `RestoreWorker.kt` (`:311`, `:399`) the line `coroutineContext.ensureActive()` sits inside a member function of a class that extends `CoroutineWorker`. The unqualified name finds the worker's own deprecated member `coroutineContext`, which is a `CoroutineDispatcher` (the compiler says so: "'val coroutineContext: CoroutineDispatcher' is deprecated"). A dispatcher holds no job, so the check can never throw. The ruled fix is `currentCoroutineContext().ensureActive()` at the three sites, which reads the context of the coroutine that is actually running and cannot be captured by the worker's member.

Why before S2 (DES-MODERNIZATION-014, as it reads at this story's writing): S2-I5 raises Kotlin to 2.4.21, and "S2-I5's Kotlin upgrade already touches how the three call sites resolve" (`:515-516`); the S2 precondition is "BUG-022 done (Record 14, row 11). Its cancellation tests are the stop rule in S2-I5" (`:556`); the stop rule itself is "the cancellation tests added by BUG-022 pass unmodified; and no Kotlin warning names `coroutineContext` in `BackupWorker.kt` or `RestoreWorker.kt`" (`:1130-1132`, also `:568`). Those tests are this story's tests. The same rule then applies in S4-C (coroutines 1.11.0) and S4-W (WorkManager 2.12.0). Why after U-066: U-066 AC-11 (a) allows no other change under `app/src/main` while it runs (`:513-514`).

Out of scope (each is a recorded Scope Concern of the bug, kept out on the bug's and the Solution Architect's advice): rethrowing `CancellationException` ahead of the broad catches so that a cancelled run does not return `Result.failure` (SC-1 of the bug; the Solution Architect recommends its own low-severity bug after this story); the pre-loop work (`checkSettings`, the restore header fetch) not being cancellable (SC-3); blocking IMAP work running on the default worker dispatcher (SC-5); the comments that say the checks work (`BackupWorker.kt:72`, `:286`, `:329`, `RestoreWorker.kt:84`, `WorkManagerCancelCollector.kt:23`), which become true by this fix and are left as they are; the incoming-backup path (BUG-021, BUG-023, separate stories); WorkManager 2.12.0 and every other upgrade (S4); any user interface.

## Decision points (the orchestrator rules before planning; the recommended option applies unless the orchestrator rules otherwise before planning)

- **DP-1: the false Javadoc in `BackupWorkerTest.kt` (`:27-31`).** It says the loops' `ensureActive()` calls "unwind the coroutine at the next suspension point" and that this is "verified at the WorkManager level". After the fix the first half is true and the second half is still false (the test only asserts WorkManager's state). The bug leaves this to the owner (its SC-2); the Solution Architect advises including this one comment, because it is the only comment that stays false. **Recommended: include it** as a comment-only edit that points to the new tests (AC-9). If the orchestrator rules it out, AC-9 is dropped and nothing else changes.
- **DP-2: how the backup loop (site 1) is reached by a test.** `backupCursors` is `private` (`BackupWorker.kt:305`), and no existing test puts rows through it. The bug's AC-2 allows "record why and what covers it instead" where a site cannot be reached, and its IC-1 allows a seam. This story does not accept the "record why" route (AC-1 requires a test that stops the backup loop). Two routes, for the plan to choose between (the plan's choice needs no ruling unless it picks a route outside these two):
  - **Route S (seam).** Widen `backupCursors` to `internal` with `@androidx.annotation.VisibleForTesting(otherwise = androidx.annotation.VisibleForTesting.PRIVATE)`, the pattern of `appendBatchAndUpdateWatermark` (U-053, `BackupWorker.kt:403-404`), and call it from a test with a hand-built `BackupCursors` (`BackupCursors()` and `add(DataType, Cursor)` are package-private in `com.zegoggles.smssync.service`, the tests' own package: `BackupCursors.java:48`, `:51`), a converter made by `WorkerEngineFactory` (`createMessageConverter`, `WorkerEngineFactory.kt:80`, public) and a recording transport. One added annotation line and one visibility keyword in production. The bug's IC-1 permits this; its AC-6 ("nothing else changes ... other than the three checks") is read with IC-1 as allowing exactly this and nothing more.
  - **Route P (provider).** No production change: drive `doWork()` through `BulkFetcher` with Robolectric content providers that answer the queries of `BackupQueryBuilder`. It ties the test to the query shape and needs fake providers for the backup side that do not exist today (the existing `FakeSmsContentProvider` is a restore-side fake).
  - **Recommended: Route S**, as the smaller and more direct. Not verified here: that a `MatrixCursor` row set converts to at least one message through `MessageConverter` (the cursor columns the converter needs were not read; `MessageConverterTest.java` builds cursors and is the model to follow). If neither route proves workable, the plan reports it to the orchestrator before any production edit; the criterion is not weakened.

## Acceptance Criteria

Terms. "The work's job" = the job of the coroutine in which the test calls the worker, so that cancelling it is what WorkManager's stop does to the worker's own job (WorkManager launches `doWork()` in a scope made of its dispatcher plus the worker's job; read from the compiled 2.9.1 classes by the Solution Architect, not re-read here). "Pass" = one iteration of the loop. "Site 1" = `BackupWorker.kt:331` in `backupCursors`; "site 2" = `RestoreWorker.kt:311` in `runImapRestoreLoop`; "site 3" = `RestoreWorker.kt:399` in `executeRestoreWithValues`. The criteria say what must be true; they do not say how the tests are written beyond the seams named. Test names given here are working names; the plan names them.

Fact the tests rely on, stated so that nobody has to rediscover it: under the unit-test harness the progress call `setProgress` is never a cancellation point (the harness's progress updater always returns a completed future and the library's fast path returns it without checking the job; Solution Architect, read from compiled 2.9.1 and work-testing 2.9.1, not re-verified here). So in a unit test the three checks are the only stop points, and a test that cancels the work's job mid-loop runs the loop to completion on the unfixed code. That is what makes each test below fail without the fix.

- [ ] AC-1 (backup loop stops at the next pass; site 1): Given a backup run with at least four rows to back up, one row per pass, and a transport that records its appends and, on its second append, cancels the work's job (the in-flight pass completes: its IMAP calls are blocking), when the loop reaches the top of the next pass, then (a) the transport saw exactly two appends and no third; (b) the watermark of the data type equals the date the second append confirmed (`appendBatchAndUpdateWatermark`, `BackupWorker.kt:404-424`), not a later one and not the starting value; (c) `closeFolders` ran exactly once and the cursors were closed (`BackupWorker.kt:375-378`, `:279-281`); (d) no `STATE_FINISHED` result was produced, shown by the test not receiving `Result.Success` with `backedUp` equal to the row count. ## Technical Context

- **Mechanism.** Kotlin resolves an unqualified name to a member of an implicit receiver before an imported top-level declaration of the same name. Inside a `CoroutineWorker` subclass `coroutineContext` is the inherited deprecated member (`CoroutineDispatcher`, default `Dispatchers.Default`, marked deprecated at warning level in WorkManager 2.9.1), not the imported `kotlin.coroutines.coroutineContext`. `CoroutineContext.ensureActive()` reads `this[Job]` and does nothing when there is none; a dispatcher holds no job. `currentCoroutineContext()` (kotlinx-coroutines; present in 1.7.3 and 1.11.0, not deprecated in either) returns the context of the running coroutine and cannot be captured by the member. These library facts are the Solution Architect's, read from the compiled classes of the named versions; this story did not re-read the libraries.
- **Versions in the build.** WorkManager `work-runtime-ktx` 2.9.1, kotlinx-coroutines 1.7.3, Kotlin 2.3.21 (bug Evidence; `app/build.gradle:155`, `:118`, `:117`). The fix does not depend on any version S2 or S4 changes.
- **Why the pass is the unit.** The IMAP calls in a pass are blocking and uninterruptible, so no check can stop a pass already running; the check acts between passes. In the backup loop one pass is one message (the bug's Suggested Approach corrects the bug body and DES-MODERNIZATION-014 D10, which say "batch": `BackupCursors.next()` moves one row, `BackupCursors.java:73-86`). In the restore loops one pass is one item.
- **Why `setProgress` is not enough, and what the unit tests rely on.** Every pass ends in `setProgress`, a suspension point at which cancellation can take effect in production when the call really suspends. Under the harness it never checks (see AC terms). So on the unfixed code the production loops usually stop one pass late and the unit-test loops never stop. Whether the production fast path also skips the check sometimes (a race) and whether WorkManager 2.12.0's replacement `await` has the same fast path were not verified; they are why the cancellation tests, not `setProgress`, are the stop rule.
- **Seams (the smallest per site; Solution Architect's analysis, re-read against the test files).** Site 3 needs none (the function is `internal` and the `RestoreInsertInterceptor.afterInsert` hook can cancel). Site 2 needs none: `doWork()` with `ImapRestoringTransport` (`RestoreWorkerIntegrationTest.kt:482`) reaches `runImapRestoreLoop`, and its `importMessageBodyImpl` lambda can cancel; the bug's remark that only one restore site has a seam undercounts. Site 1 needs DP-2.
- **How a test cancels the work's job without cancelling itself.** The tests call `doWork()` or `executeRestoreWithValues` inside `runBlocking`, so the work's job is the test's own coroutine. A caution, from reasoning about coroutine semantics and not run: if the test cancels the `runBlocking` coroutine itself, `runBlocking` rethrows a `CancellationException` at the end even if the body returned a value, so the test should run the call in a child (`launch { ... }`) whose job it holds, cancel that job from the fixture, and `join()` it; the result of a cancelled run is then read from a variable the child set, not from `await()`. The plan confirms the form that works.
- **Test helpers present.** `TestListenableWorkerBuilder`, `WorkManagerTestInitHelper.initializeTestWorkManager` (`BackupWorkerIntegrationTest.kt:76-90`, `RestoreWorkerIntegrationTest.kt:88-99`, needed because `doWork` calls `setForeground`), `runBlocking` (the worker tests use it; the design notes the repository's coroutine tests use `runTest` and `UnconfinedTestDispatcher` elsewhere), Robolectric, `FakeSmsContentProvider` registered for the `sms` authority. No test dispatcher is needed: the loops have no delay and the fixture cancels from inside a blocking callback.
- **Not verified here (no Gradle run was allowed).** That any of the new tests compiles or behaves as described; that `config.maxRestore` leaves `itemsToRestoreCount` at the number of handles in the restore fixture (the restore tests that run `doWork` with handles suggest so); that a `MatrixCursor` fixture converts to messages (DP-2); that `StubMailTransport` can cancel on a chosen append; the library behaviours above.
- **Estimation.** Complexity low in production (three call lines, two imports, optionally one seam), moderate in tests (seven or more tests across three classes, the backup fixture being the largest part), six mutations with restores, the gate run twice. It fits one sprint as one story: one defect, three sites, one mechanism. Seven criteria beyond the gates exist because each site needs its own proof and its own mutation. Expect about eight to twelve Gradle invocations.
