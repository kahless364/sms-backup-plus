# U-063: Characterisation Tests for the Two TLS Socket Factories

## Story
As the product owner and sole user of this private, unpublished SMS Backup+ build,
I want tests that record how the app's two TLS socket factories (`DefaultTrustedSocketFactory` for `SYSTEM_VALIDATED`, `PinnedCertificateSocketFactory` for `PINNED_CERTIFICATE`) behave today, including a real loopback TLS handshake for host-name mismatch, untrusted chain and expired chain,
So that when the default factory and its trust manager (about 458 lines, mostly untested) are moved into app-owned code, the move is checked against a recorded baseline and cannot silently drop host-name verification, chain validation, the SNI guard or cipher and protocol hardening while the whole suite stays green.

Product owner decision (verbatim, 2026-11-17, Record 5 item 5 of the U-062 analysis appendix "Product owner decision"): "yes. add tests". The story is created from CR-009 and does not wait for the migration. It describes today's behaviour only.

## Scope and Delivery Shape

One story, tests only. No production behaviour changes, no code moves, no contract edit. Ordered increments, each committed separately; `:app:assembleDebug :app:testDebugUnitTest` must pass after each (the full gate runs at I0 and I7).

### Group B: host-name mismatch under SYSTEM_VALIDATED (T3)

Common set-up for Groups B and C (design hints are in Technical Context, "Test mechanics"): a loopback `SSLServerSocket` bound to the loopback address on an OS-chosen port presents one certificate chosen by the test; the client socket comes from `new DefaultTrustedSocketFactory(<application>).createSocket(...)` and is connected to the loopback address; the handshake is triggered with `startHandshake()` (the product triggers it lazily on the first read, `ImapConnection.java:119`, which is the same handshake). Rejection is observed at the handshake, not in `createSocket`; see Scope Concern SC-1. In every rejection test the failure must be an `SSLException` whose direct `getCause()` is a `java.security.cert.CertificateException`, because `ImapConnection.handleSslException` (`ImapConnection.java:146-152`) turns an `SSLException` into a `CertificateValidationException` (the "Certificate error" path) only under that condition.

- [ ] AC-5: (implicit TLS, control) The server presents the `right-host` chain (leaf with SAN dNSName `imap.right.test`, signed by the test CA that the test installs as the trust anchor). The client, created with host `imap.right.test` through `createSocket(null, host, port, null)`, completes the handshake without exception, and a byte written by the server after the handshake is read by the client. Breaks when: the trust manager or the host-name check rejects a valid chain, for example `verifyHostname` is called with the wrong host, or `MinimalSslSession.getPeerCertificates()` (`TrustManagerFactory.java:164-166`) returns an empty array. This control is what stops AC-6 from passing for the wrong reason (see E3 in Technical Context).
- [ ] AC-6: (implicit TLS, mismatch) The server presents the `other-host` chain (same test CA, SAN dNSName `imap.other.test`). The client asks for `imap.right.test`. `startHandshake()` throws an `SSLException` with a `CertificateException` as direct cause; that cause is a `com.fsck.k9.mail.CertificateChainException`; and the message of the cause chain contains `was not verified against the server certificate` (`TrustManagerFactory.java:147-148`), which proves that the rejection came from the host-name check and not from chain validation. Breaks when: the call `verifyHostname(mHost, chain)` at `TrustManagerFactory.java:77` is removed, or the trust manager installed by `createSocket` (`DefaultTrustedSocketFactory.java:155`) is replaced by an accept-all `X509TrustManager`.
- [ ] AC-7: (STARTTLS upgrade, control) The server accepts a plain connection, writes one plain line, then upgrades the same connection to TLS and presents the `right-host` chain. The client reads the plain line from the plain socket, then calls `createSocket(plainSocket, "imap.right.test", port, null)` (the call shape of `ImapConnection.java:315`), and the handshake completes; a byte written by the server after the upgrade is read. Breaks when: as AC-5, or when the layered branch `socketFactory.createSocket(socket, host, port, true)` (`DefaultTrustedSocketFactory.java:172`) is replaced by returning the plain `socket`.
- [ ] AC-8: (STARTTLS upgrade, mismatch) As AC-7 with the `other-host` chain. Same assertions as AC-6. Breaks when: as AC-6.

### Group D: cipher and protocol hardening (T5)

What the code does, as read on 2026-11-17 (`DefaultTrustedSocketFactory.java:34-148`, `:182-189`): the cipher list is the provider's default enabled suites, with the 16 names in `BLACKLISTED_CIPHERS` removed, the 24 names in `ORDERED_KNOWN_CIPHERS` placed first in that order, and every other suite appended in its original order (`reorder`, `:124-148`). The protocol list is built the same way from the provider's **supported** protocols (not the enabled ones, `:107`, `:116`), with only `SSLv3` removed and `TLSv1.2, TLSv1.1, TLSv1` placed first in that order. TLS 1.0 and 1.1 are therefore not removed, and a protocol the provider supports that is not in the known list (for example `TLSv1.3`, `SSLv2Hello`) is appended after `TLSv1`. `hardenSocket` applies both lists to the socket if they are non-null (`:182-189`); `createSocket` calls it before `setSniHost` on both paths (`:176`). No test below asserts a property the code does not have. Expected values come from the live provider at test time plus the literal baseline pinned in AC-14; they are never a hard-coded list of provider suites.

- [ ] AC-11: A test `reorder_removesEveryBlockedItem` calls the protected static `reorder` by reflection with an input made of the 16 literal blocked cipher names of AC-14 plus two known and one unknown cipher, and the class's own `ORDERED_KNOWN_CIPHERS` and `BLACKLISTED_CIPHERS`; it asserts that no blocked name is in the result and the three others are. A second assertion does the same for the protocol input `{SSLv3, TLSv1.2, X}` with the class's protocol constants. Breaks when: any name is removed from `BLACKLISTED_CIPHERS` (`:64-81`) or `SSLv3` is removed from `BLACKLISTED_PROTOCOLS` (`:87-89`), or the removal loop at `:129-133` is deleted.
- [ ] AC-12: A test `reorder_ordersKnownItemsFirst_thenUnknownInOriginalOrder` calls `reorder` with a shuffled subset of the literal known ciphers, then two unknown names `U1`, `U2` in a fixed order, and asserts the result lists the known names in the literal order of AC-14, followed by `U1`, `U2` in that order. It repeats this for the protocols `{TLSv1, X, TLSv1.2, Y, TLSv1.1}`, expecting `TLSv1.2, TLSv1.1, TLSv1, X, Y`. Breaks when: two entries of `ORDERED_KNOWN_CIPHERS` or `ORDERED_KNOWN_PROTOCOLS` are swapped, or the unknown items are put first or dropped (`:143-145`).
- [ ] AC-13: A test `reorder_withNullBlocklistAndEmptyInput_behavesAsRecorded` asserts: a `null` blocklist keeps every input item (`:129`), and an empty input gives an empty array. Breaks when: the `blacklisted != null` guard is removed (NullPointerException) or empty input is mishandled.
- [ ] AC-14: Two tests, `cipherConstants_matchRecordedBaseline` and `protocolConstants_matchRecordedBaseline`, read `ORDERED_KNOWN_CIPHERS`, `BLACKLISTED_CIPHERS`, `ORDERED_KNOWN_PROTOCOLS` and `BLACKLISTED_PROTOCOLS` by reflection and assert each equals a literal array in the test: the 24 ordered known cipher names (`:37-62`), the 16 blocked cipher names (`:64-81`), `{TLSv1.2, TLSv1.1, TLSv1}` and `{SSLv3}`. These are snapshot tests; their purpose is that any edit to a list during or after the move is a conscious, reviewed change. Breaks when: any entry of any of the four lists is added, removed, reordered or renamed.
- [ ] AC-15: A test `createSocket_enabledCipherSuites_areProviderDefaultsMinusBlockedWithKnownFirst` creates a socket with `createSocket(null, "imap.right.test", 993, null)` and compares `getEnabledCipherSuites()` with the provider default set (read from a fresh `SSLContext.getInstance("TLS")` initialised with `init(null, null, null)` and an unconnected socket from its factory). It asserts: (i) the sets are equal after removing the literal blocked names from the default set; (ii) the known ciphers present appear in the literal order of AC-14; (iii) every known cipher precedes every unknown cipher. Breaks when: `hardenSocket(sslSocket)` at `DefaultTrustedSocketFactory.java:176` is removed (the order and set are then the provider's), or `sock.setEnabledCipherSuites` at `:184` is removed.
- [ ] AC-16: Two tests on the same socket. `createSocket_enabledProtocols_areProviderSupportedMinusSslv3_inRecordedOrder` asserts: `SSLv3` is not enabled; the enabled set equals the provider's supported set minus `SSLv3`; among the protocols present, `TLSv1.2` precedes `TLSv1.1` precedes `TLSv1`, and all of these precede any other protocol. `createSocket_legacyProtocols_remainEnabled_whenProviderSupportsThem` asserts, for each of `TLSv1` and `TLSv1.1`, that it is enabled if and only if the provider lists it as supported. The second test records, as a named characterisation, that TLS 1.0 and 1.1 are not removed by the factory (see DP-2 and AC-23). Breaks when: `ENABLED_PROTOCOLS` is built from `getEnabledProtocols()` instead of `getSupportedProtocols()` (`:107`), `TLSv1` or `TLSv1.1` is added to `BLACKLISTED_PROTOCOLS`, or `hardenSocket` stops calling `setEnabledProtocols` (`:187`). The environment probe (IC-11) records whether the live provider supports TLS 1.0 and 1.1 and whether it enables them by default; if the provider's default already enables both, the second test cannot tell the factory from the provider and the story reports that in its notes rather than claiming the mutation is caught.
- [ ] AC-17: A test `createSocket_layeredOverPlainSocket_appliesSameHardening` opens a plain loopback connection (a `ServerSocket` on the loopback address, port 0, one accept, no TLS), calls `createSocket(plainSocket, "imap.right.test", <port>, null)`, and asserts the result is an `SSLSocket` whose enabled cipher suites and enabled protocols are equal, in order, to those from AC-15 and AC-16 on the implicit path. No handshake is run. Breaks when: `hardenSocket` is made to run only when `socket == null`.

### Facts established (read on 2026-11-17)

- **E1. - **E2. TLS provider.** The Robolectric Android 10 jar contains no `javax/net` entries (checked by listing it), so `javax.net.ssl.*` comes from the JDK. - **E3. Host-name verifier in the test JVM (important).** `TrustManagerFactory.verifyHostname` (`:142-150`) asks `HttpsURLConnection.getDefaultHostnameVerifier()`. On a desktop JDK that default verifier is, to my knowledge of the JDK source, a stub that returns `false` for every host; on a device it is the platform's real verifier. If the probe confirms the stub, then every `SYSTEM_VALIDATED` handshake fails host-name verification in the unit-test JVM, and (a) a mismatch test would pass vacuously, and (b) the control cases AC-5 and AC-7 cannot pass. - **E4. Trust anchor.** `TrustManagerFactory.defaultTrustManager` is a `private static` (not `final`) field filled once at class initialisation from the platform default trust store (`TrustManagerFactory.java:33`, `:102-117`). The chain validation is then the platform's PKIX validator against a trust store the test controls; the machine's trust store plays no part. `SecureX509TrustManager` instances are cached per `host:port` but read the static field on every call (`:76`), so the swap works with cached instances.

### Test mechanics (design hints that remove ambiguity; not a plan)

- **Loopback server (`LoopbackTlsTestServer`).** An `SSLServerSocket` from an `SSLContext` whose key manager holds the chosen fixture chain and key, bound with port 0 to `InetAddress.getLoopbackAddress()`, `setSoTimeout` at most 10 s, one daemon thread that accepts once and reports its outcome through a `Future`. Implicit mode: handshake, write one byte, close. STARTTLS mode: write one plain line (for example `* OK`), then wrap the accepted socket with `sslSocketFactory.createSocket(plain, null, port, true)`, `setUseClientMode(false)`, handshake, write one byte. The server side's own failure on a rejected handshake (alert or reset) must not fail the test or hang it.
- **Client side.** `new DefaultTrustedSocketFactory(RuntimeEnvironment.getApplication())`. Implicit: `(SSLSocket) factory.createSocket(null, host, port, null)`, then `connect(new InetSocketAddress(InetAddress.getLoopbackAddress(), port), 10000)`, `setSoTimeout(10000)`, `startHandshake()`. STARTTLS: open a plain `Socket` to the loopback address, read the plain line, then `factory.createSocket(plainSocket, host, port, null)` and `startHandshake()`.
- **Walking the exception.** A small helper returns the first `Throwable` in the cause chain whose message contains a given text. Do not assert provider-specific exception classes below `CertificateException`.
- **Reflection.** `reorder` and the four lists are `protected static` (`DefaultTrustedSocketFactory.java:34-89`, `:124`), `isIpOrBlankHostname` is package-private (`:216`). Reflection with `setAccessible(true)` is used, as the existing SNI test does for `setHostnameViaReflection` (`DefaultTrustedSocketFactorySniTest.java:250-260`). When the class moves, those reflective lookups are retargeted with the class; that is a Part B task.
- **Mutation runs.** Make each edit in the working tree only; never commit one.
