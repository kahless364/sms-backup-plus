# U-065: Drop TLS Versions Older Than 1.2 From Both TLS Socket Factories, and Give the Pinned-Certificate Factory the Default Factory's Cipher-Suite and Server-Name Handling

## Story
As the owner of this private, unpublished SMS Backup+ build (its only user, whose mail password travels over this connection),
I want neither TLS socket factory to enable any protocol version older than TLS 1.2, and the pinned-certificate factory to treat cipher suites and the server name exactly as the default factory does,
So that every mail connection carries the password under one tested minimum whichever trust policy chose the factory, and a later change cannot let the two factories drift apart without a test failing.

One story closes two ready bugs, on the product owner's decisions of 2026-11-20:

- BUG-019 (`sdlc/artifacts/stories/BUG-019-factory-enables-tls10-and-tls11.md`): the default factory (`k9mail-vendored/src/main/java/com/fsck/k9/mail/ssl/DefaultTrustedSocketFactory.java`) enables TLS 1.0 and TLS 1.1 wherever the provider supports them.
- BUG-020 (`sdlc/artifacts/stories/BUG-020-pinned-factory-no-tls-hardening.md`): the pinned-certificate factory (`app/src/main/java/com/zegoggles/smssync/mail/PinnedCertificateSocketFactory.java`) applies none of the default factory's protocol, cipher-suite or server-name handling.

### Decisions this story implements (binding input, not re-opened)

The decisions are in the appendix "Product owner decision" of `sdlc/artifacts/build/feasibility/U-062/thunderbird-mail-libraries-feasibility-analysis.md`. The words below are copied from the two records.

| Record | Question | Verbatim answer | Decision, as the record states it |
|--------|----------|-----------------|-----------------------------------|
| Record 8 (2026-11-20) | BUG-019 and BUG-020, protocol versions: "drop TLS 1.0 and 1.1 for both factories, or keep them?" | "Yes drop anything older than tls 1.2" | "Neither factory enables a protocol version older than TLS 1.2: not TLS 1.0, not TLS 1.1, not SSLv3 (already blocked in the default factory), and not the legacy `SSLv2Hello` hello format, which is older than TLS 1.2 in the sense of the answer. TLS 1.2 and TLS 1.3 stay enabled where the platform supports them. Accepted compatibility cost: a server that offers nothing newer than TLS 1.1 can no longer be used; the measurement showed Gmail's IMAP endpoint accepts TLS 1.2 and negotiates TLS 1.3" |
| Record 9 (2026-11-20) | BUG-020, cipher suites: "Does the pinned factory get the default factory's cipher handling?" | "Same as default" | "The pinned factory applies the same cipher-suite handling as the default factory (the same order and the same blocked list)". Not decided by the record: "How the two factories share the handling in code (one shared step, a call into the default factory's step, or a copy); that is for the fix story's plan" |
| Record 9 | BUG-020, server name: "Does it set the server name itself, or leave it to the platform?" | "Same as default" | "The pinned factory sets the server name by the same rule as the default factory: the host for a DNS name; none for an IP address or a blank or missing host; a name the platform rejects causes no failure" |
| Record 9 | Timing of the fix | "Same as default" (reply to the orchestrator's statement of the plan) | Orchestrator's reading, recorded as such in Record 9: "the fix is its own story in sprint 021, after U-064, before and separate from the migration's code move. The product owner did not object to that plan" |

Out of scope: the contract `CNTR-MODERNIZATION-001` and every change record (the product owner holds contract changes for one combined revision at the migration), the migration's move of the default factory into app-owned code (CR-009), certificate trust and host-name checks, any user interface.

## Acceptance Criteria

Terms: "direct" socket = `createSocket(null, host, port, alias)`; "layered" socket = `createSocket(plainSocket, host, port, alias)` over an already connected plain socket (the STARTTLS shape). "Conscrypt" and "JDK" provider = the two test providers: Robolectric's default (Conscrypt) and the JDK's own (SunJSSE) used by `DefaultTrustedSocketFactoryJdkProviderTest` (with its two annotations and its three isolation guards). "The old four" = `TLSv1`, `TLSv1.1`, `SSLv3`, `SSLv2Hello`. Test names that exist today are given by method name, because the line numbers cited in the bugs are stale (see Technical Context, "Facts established"). New tests are named by the plan; the names here are working names.

- [ ] AC-1 (protocol floor, default factory): Given `new DefaultTrustedSocketFactory(context)` under the Conscrypt provider and, separately, under the JDK provider, when `createSocket` returns a direct socket and a layered socket, then for each of the four combinations:
  - (a) `getEnabledProtocols()` contains none of the old four.
  - (b) `TLSv1.2` and `TLSv1.3` are each enabled if and only if the provider's `getSupportedProtocols()` lists them. This is the decided meaning of "where the platform supports them": the test is against the provider's supported list, as the code reads it today (`DefaultTrustedSocketFactory.java:102-107`), not against its default-enabled list. Together with (a): the enabled set is exactly the provider-supported protocols that are TLS 1.2 or newer. On both test providers that is `{TLSv1.2, TLSv1.3}` (supported lists: Conscrypt `I0-probe.txt:26`; JDK `I0c-diag.txt:7`).
  - (c) The assertion cannot pass on the provider's own defaults. Under Conscrypt the test first asserts, as a precondition with a message, that the provider's default socket has `TLSv1` and `TLSv1.1` enabled (it does: `I0-probe.txt:27`), so their absence on the factory's socket can only be the factory's doing. Under the JDK provider the existing precondition A1-P2 stays (the two are supported and not enabled by default, `I0c-diag.txt:7-8`).
  - (d) Widening, stated as the decided result and not as code: no protocol older than TLS 1.2 is ever enabled, however the provider lists or enables it. A protocol is enabled only if the provider supports it. TLS 1.2 and TLS 1.3 are enabled whenever supported, including a provider that supports one and leaves it off by default (this is "stay enabled where the platform supports them", read literally). Neither test provider is such a provider (both enable both by default), so (b) alone cannot tell "built from the supported list" from "built from the enabled list" for these two. Where the plan's structure allows the protocol step to be fed a given supported list, a test feeds `{SSLv2Hello, SSLv3, TLSv1, TLSv1.1, TLSv1.2, TLSv1.3}` and expects exactly `{TLSv1.2, TLSv1.3}`, and feeds `{TLSv1.2}` and expects `{TLSv1.2}`. If the structure does not allow it, Implementation Notes record that this distinction is untested and why (see Scope Concerns, 5).
  - (e) The branch where the provider query failed at class initialisation (both static lists null, `:108-117`; `hardenSocket` then applies nothing, `:183-188`, so the platform's own defaults would stand) either also yields no protocol older than TLS 1.2, shown by a test that forces that branch, or Implementation Notes record why a test cannot force it and what the code does there. It is not left unmentioned (Scope Concerns, 4).
- [ ] AC-2 (protocol floor, pinned factory): Given `new PinnedCertificateSocketFactory(context, host, enrolledCert)` under both test providers, when `createSocket` returns a direct and a layered socket, then:
  - (a) the same result as AC-1 (a) and (b) holds on all four combinations.
  - (b) Under Conscrypt the assertion cannot be met by the provider's defaults (same precondition as AC-1 (c)); this is where the pinned factory's floor is proved.
  - (c) Under the JDK provider the enabled set is exactly `{TLSv1.2, TLSv1.3}`, so a pinned factory that took the default factory's old logic (every supported protocol except SSLv3) would be caught: it would add `TLSv1`, `TLSv1.1` and `SSLv2Hello`, which the JDK provider supports and leaves off by default (BUG-020 Suggested Approach, first refinement: the pinned socket gains no protocol the provider had disabled).
- [ ] AC-3 (cipher suites, pinned factory): Given the pinned factory and the default factory built in the same test, under both test providers, when each returns a direct and a layered socket, then:
  - (a) Parity: the pinned socket's `getEnabledCipherSuites()` equals the default factory's socket's, in the same order. A pinned factory that changes nothing fails this on both providers, because neither provider's own order is the factory's order (Conscrypt: `I0-probe.txt:47`, `cipher_order_differs=true`; JDK: the default list begins `TLS_AES_256_GCM_SHA384` and the factory's list begins `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384`, `I0c-diag.txt:14` against `:16`). The assertion is therefore made through order.
  - (b) Against the recorded rule, not only against the other factory: under Conscrypt the pinned direct socket passes the same three checks as `createSocket_enabledCipherSuites_areProviderDefaultsMinusBlockedWithKnownFirst` (the set equals the provider's default set minus the literal blocked names; the known suites appear in the literal order; every known suite precedes every unknown one, with the provider-fixed suites set aside as that test does), using the literal baselines `KNOWN_CIPHERS_BASELINE` and `BLOCKED_CIPHERS_BASELINE`. This stops both factories being wrong the same way.
  - (c) Blocked list: neither test provider's default list contains a blocked suite (Conscrypt `I0-probe.txt:33`, `blocked_in_default=[]`; JDK: none of the 16 names appears in `I0c-diag.txt:14`), and the step reads only the enabled list, so a socket-level test cannot show a blocked suite being removed. The pinned factory's blocked list is therefore asserted where a blocked name can be fed in, at the step's input: if the pinned factory calls the default factory's step, the existing `reorder_removesEveryBlockedItem` and `cipherConstants_matchRecordedBaseline` cover the list and the mutation in AC-7 covers the call; if the pinned factory holds a copy, the copy gets the same two checks, or one test compares the copy's lists with the default factory's by reflection. No provider, fixture or context that offers a blocked suite is invented; if the plan finds a provider whose default list does contain one, the socket-level removal is asserted there too.
- [ ] AC-4 (server name, pinned factory): Given the pinned factory under the JDK provider (the only test provider where `getSSLParameters().getServerNames()` reports what is set; under Conscrypt it reports nothing whatever is set, `I0-probe.txt:24-25`), when `createSocket` returns a direct socket for each host below, then the socket reports what statements S1 to S6 of CR-013 say the default factory sets (CR-013, section "Proposed Change", Edit 3, table at `:311-318`, is the reference wording):

  | Statement | Host given | Pinned socket must report |
  |-----------|------------|---------------------------|
  | S1 | a DNS-form name the platform accepts | exactly one server name, an `SNIHostName` equal to the host |
  | S2 | four dot-separated groups of one to three digits (for example `192.168.1.10`) | no server name; `createSocket` does not throw |
  | S3 | a host containing a colon (`::1`, `fe80::1`, the eight-group literal) | no server name; `createSocket` does not throw |
  | S4 | null, empty, and blank | no server name; `createSocket` does not throw |
  | S5 | a name that passes the S2 to S4 checks and `SNIHostName` rejects (`bad_host.example`, `host.example.`, `-x.example`, the names U-064 uses) | no server name; `createSocket` does not throw; the socket is returned |
  | S6 | any of the above | the only name ever set is the host |

  - (a) The existing test `pinnedFactory_createSocket_implicit_setsNoServerNames_jdkProvider` is changed to assert S1 (its control, `createSocket_dnsHost_setsServerNameOnRealSocket`, stays as it is). It cannot pass on the provider's behaviour alone: an unconnected direct socket has been given no host by the provider, so only the factory's own step can put a name on it (U-063's mutation M-E2-jdk showed that the observable reports a name the factory sets, under the JDK provider).
  - (b) Layered shape: conditional. It is asserted in the same way only if a probe, run first and recorded, shows that on a layered JDK socket `getSSLParameters().getServerNames()` reports only what the factory set (the provider may add a name on its own, which is why U-063 did not assert the layered shape, `DefaultTrustedSocketFactoryJdkProviderTest.java:308-309`). If the provider adds the name itself, the layered shape cannot tell the factory's step from the provider's; then only "no exception and an `SSLSocket` is returned" is asserted for S2 to S5, and the reason is recorded in Implementation Notes. It is not left silently weaker.
  - (c) Null host (S4) is asserted on the direct shape. On the layered shape the provider may itself refuse a null host; if the plan shows that, the case is recorded as provider behaviour and not asserted.
  - (d) The protocol floor (AC-2) and the cipher order (AC-3) are asserted on the same socket after the server-name step has run, because that step reads and writes the socket's parameters (`DefaultTrustedSocketFactory.java:244-247`) and could undo the earlier settings if the steps were ordered wrongly.
- [ ] AC-5 (the factories cannot drift): Given both factories built in one test, when a future edit changes the protocol, cipher-suite or server-name handling of one factory only, then a test fails. It must fail on each of the three drifts in AC-7 (M-P6). It does not prescribe how the code is shared.

### The widening point (the architect's trap)

The default factory builds its protocol list from what the provider supports and its cipher list from what the provider enables (`:107` against `:100`). Its cipher step can therefore only reorder or remove, but its protocol step can switch on a version the platform turned off. That is exactly what the JDK-provider evidence shows: the factory enables `TLSv1`, `TLSv1.1` and `SSLv2Hello` where SunJSSE leaves them off (`I0c-diag.txt:8` against `:15`). Copying the default protocol step onto the pinned socket unchanged would widen the pinned path. The decided result, independent of code: no protocol older than TLS 1.2 is enabled on either factory's socket; TLS 1.2 and 1.3 are enabled where the provider supports them; nothing the provider does not support is enabled. AC-1 (d) and AC-2 (c) state it as testable. The one consequence of the literal reading ("supports", not "enables by default") that no available evidence shows: on a provider that supports TLS 1.2 or 1.3 and leaves it off by default, the pinned socket now has it on. Both test providers enable both by default; the Android 16 and Android 11 emulators list both as enabled by default (BUG-019 measurements). See Scope Concerns, 3.

### Test providers and their limits (from U-063 Implementation Notes and the fixtures)

- Under the Conscrypt provider (Robolectric default, simulated API level 29 on a desktop JDK 25), supported protocols equal enabled protocols for the factory's purposes: both `[TLSv1, TLSv1.1, TLSv1.2, TLSv1.3]` (`I0-probe.txt:26-27`), so the factory's part cannot be separated from the provider's by a set comparison of the default socket; the new absence assertions work because the provider's defaults contain the old versions. A client socket reports no server names whatever is set (`I0-probe.txt:24-25`).

- The loopback server always wraps an accepted plain socket and passes the loopback address string as the peer host, because Conscrypt's server side otherwise reflects into JDK internals (`LoopbackTlsTestServer.java:39-42`). An added protocol option must keep that.
