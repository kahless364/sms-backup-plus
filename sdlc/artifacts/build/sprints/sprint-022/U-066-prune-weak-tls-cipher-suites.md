# U-066: Prune the Weak Cipher Suites From the Lists Both TLS Socket Factories Share, and Close the Failed-Initialisation Branch for Cipher Suites

## Story
As the owner of this private, unpublished SMS Backup+ build (its only user, whose mail password travels over this connection),
I want both TLS socket factories to enable only cipher suites that give forward secrecy with authenticated encryption, and none of the weak suites the lists still allow,
So that the connection that carries the password cannot be settled on a suite current guidance retires, and so that the migration's code move (CR-009) carries lists that are already pruned and tested.

The sentence above states the recommended target (decision DP-1, option A). If the orchestrator rules another option before planning, the planning step rewrites the middle line to that option and the criteria marked "if another option is ruled" change as stated.

Source: finding F-1 (Low) of the U-065 security review (`sdlc/artifacts/build/sprints/sprint-021/U-065/review-security.md`), and the product owner's decision of 2026-11-21, Record 11, answer 2, verbatim "2 yes": a story prunes the weak cipher suites from the lists the two factories share, before the migration's code move; "which suites go is decided in that story, with the product owner where a choice costs compatibility". There is no REQ-* source. The contract side is change record CR-014 (`sdlc/artifacts/build/change-records/CR-014-cntr-001-state-protocol-floor-and-cipher-handling.md`, approved, not applied), which states the cipher handling as a rule (statements C1 to C3, prepared C4, B1 to B3) and lists what this story must respect (section "The cipher-pruning story: what it must do to keep this record's text true", points 1 to 11, and its Scope Concerns A and B with the architect's rulings).

Out of scope: the protocol floor (U-065), the server-name handling, certificate trust and host-name checks, the migration's move of the default factory (CR-009), making the shared arrays private or unmodifiable (U-065 security review F-4: it belongs with the move), the contract and every change record (the product owner holds contract changes for one combined revision; this story edits none and hands the orchestrator the exact rewording, AC-10), the OAuth and contacts connections (U-065 review F-6), any user interface.

## Decision points (the orchestrator rules before planning; the recommended option applies unless the orchestrator rules otherwise before planning)

Record 12 (2026-11-21): routine choices are the orchestrator's, on the recommendation of the agent that owns the question; a decision that costs compatibility for a device or server in use goes to the product owner. Only DP-1 can cost compatibility. On the evidence in the repository it is a routine choice: the only server the owner uses is Gmail's mail server (U-065, Technical Context, "Measurements on two emulators"), and the owner said of any enrolled pinned host "I don't think so" (Record 7, item 3; not checked on a device). If the orchestrator knows of any other server or device in use, DP-1 goes to the product owner. Implementation Notes record who ruled each point (AC-13).

Terms used below. TLS13 = the three TLS 1.3 suites `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256`. AEAD12 = the six TLS 1.2 suites `TLS_ECDHE_{RSA,ECDSA}_WITH_AES_{256,128}_GCM_SHA{384,256}` and `TLS_ECDHE_{RSA,ECDSA}_WITH_CHACHA20_POLY1305_SHA256`. CBC12 = the four `TLS_ECDHE_{RSA,ECDSA}_WITH_AES_{256,128}_CBC_SHA`. SCSV = `TLS_EMPTY_RENEGOTIATION_INFO_SCSV`, a signalling value that is listed with the suites but is never negotiated as one.

### DP-1: the target policy

| | Suites that stay enabled | Blocked | A server must offer | What stops working | On the test providers |
|---|---|---|---|---|---|
| **A (recommended)**: forward secrecy with authenticated encryption only | TLS13, AEAD12, SCSV (10 names) | everything else: CBC, SHA-1 MAC, RSA key exchange, static ECDH, DHE, 3DES, DSS, null, anonymous, export, RC4 | TLS 1.3, or TLS 1.2 with an ECDHE suite using AES-GCM or ChaCha20-Poly1305 | A TLS 1.2-only server whose suite list has no ECDHE AEAD suite: CBC-only, DHE-only or static-RSA-only (from general knowledge, older Windows-based mail servers and old firmware; not measured). No such server is known to be in use | Conscrypt 18 names to 10 (8 removed: 4 ECDHE CBC-SHA, 2 RSA-key-exchange GCM, 2 RSA-key-exchange CBC-SHA). JDK 31 to 10 (21 removed: 13 DHE, 4 ECDHE CBC with SHA-256 or SHA-384, 4 ECDHE CBC-SHA) |
| **B**: A plus ECDHE with AES-CBC | A plus CBC12 (14 names) | as A, minus CBC12 | as A, or TLS 1.2 with ECDHE-CBC | only a TLS 1.2 server with DHE-only or static-RSA-only suites | Conscrypt 18 to 14. JDK 31 to 14 (the SHA-256 and SHA-384 CBC forms are not in CBC12: Android does not enable them, only the desktop JDK does) |
| **C**: remove only what is plainly broken or pointless | everything the platform enables except: 3DES, DSS, static ECDH (`TLS_ECDH_*`), and any `TLS_*` null, anonymous, export or RC4 name. Static RSA key exchange (`TLS_RSA_*`) **stays**, and so do DHE-RSA and CBC | those categories | what is offered today | nothing realistic | Conscrypt 18 to 18: none of its 18 default suites is in those categories, so C changes nothing on that provider and no test can show it. JDK 31 to 25 (6 DHE-DSS removed) |

Facts behind the table (verified): the Conscrypt default list is `I0-probe.txt:30` (18 names), the JDK default list is `I0c-diag.txt:14` (31 names), both under `sdlc/artifacts/build/sprints/sprint-020/U-063/evidence/`. Both providers' defaults contain all ten names of option A (TLS13, the six AEAD12 names, SCSV), so under A both providers must end with the same ten. The public guidance relied on (RFC 9325, "Recommendations for Secure Use of TLS and DTLS", BCP 195, read on 2026-11-21 at its published text): section 4.1 "MUST support and prefer to negotiate cipher suites offering forward secrecy", "SHOULD NOT negotiate cipher suites based on RSA key transport" (static RSA), "SHOULD NOT negotiate" static DH or static ECDH, "SHOULD NOT negotiate" the `TLS_DHE_*` suites in TLS 1.2, "MUST NOT negotiate" RC4 and NULL-encryption suites and suites under 112 bits (export); section 4.2 lists four TLS 1.2 suites as RECOMMENDED, exactly `TLS_ECDHE_{RSA,ECDSA}_WITH_AES_{128,256}_GCM_SHA{256,384}`, and says a CBC suite "SHOULD NOT be used unless the `encrypt_then_mac` extension is also successfully negotiated"; section 4.3 specifies no TLS 1.3 suites. RFC 9325 does not name ChaCha20-Poly1305 and does not mention anonymous suites in sections 4.1 to 4.5. RFC 8996 (cited by U-065) is the protocol side.

Not measured: that Gmail offers ECDHE-GCM or ChaCha20 at TLS 1.2 (the product owner's brief says it does; BUG-019 recorded only that a handshake limited to TLS 1.2 was accepted, with the suite not recorded, and that every unrestricted handshake negotiated TLS 1.3); whether the platform's providers negotiate `encrypt_then_mac`; the default cipher lists of the Android 16 and Android 11 emulators (not in BUG-019 or any evidence file in the repository: step S0-3).

Recommendation: **A**. Reasons: (1) it is the only option that meets F-1's substance and RFC 9325 sections 4.1 and 4.2 together (forward secrecy, no static RSA, no DHE, no CBC without encrypt-then-MAC); (2) Gmail is unaffected on the path it takes (TLS 1.3); (3) the cost falls only on servers nobody is known to use, the same trade the owner accepted for the protocol floor (Record 8); (4) C does nothing on a real Android provider (the platform already leaves 3DES, DSS and static ECDH off) and leaves non-forward-secret suites enabled, so it would close the finding on paper only; (5) B keeps SHA-1 CBC, which RFC 9325 discourages, for a server class not known to exist; it is the fallback if the orchestrator or the product owner knows of such a server. A keeps the two ChaCha20-Poly1305 TLS 1.2 suites although RFC 9325 does not name them (they are authenticated encryption with forward secrecy, and Android enables them); if the orchestrator wants exactly RFC 9325's four, those two names leave the allowed set and every list below shrinks by two.
If another option is ruled, these criteria change: the expected lists in AC-1, AC-2 and AC-3 (B: the 14 names; C: the provider default minus the named categories, known first, 18 on Conscrypt and 25 on JDK), AC-3's category set (B: CBC with SHA-1 on ECDHE is allowed; C: only 3DES, DSS, static ECDH, null, anonymous, export and RC4 are checked), the allowed-constant check in AC-3 (b), and mutation M-X1's put-back examples.

Recommendation: **allow-list**. The product owner's decision is a claim about what is enabled; only an allow-list can make "no weak suite is enabled" true for names no one has listed, and the security review recommended it (F-1: "an allow-list of ECDHE+AEAD suites plus the TLS 1.3 suites would be the safer shape"). It matches the protocol allow-list U-065 chose, and the price (CR-014 reworded first, a code change when a new suite is wanted) is small for a private app against one server. How the allowed list and the preferred order are held in code (one ordered constant, or the allow-filter applied after `reorder` as `protocolsToEnable` does) is for the plan; if a blocked list is kept beside an allow-list, a test must fail when it is emptied, otherwise it is dead and goes.
If the blocklist is ruled instead: AC-3 (b) and (c) apply to the blocked list (every pruned name is on it); AC-1 and AC-2 expected lists need the extra unknown-name blocks (the JDK-only DHE, CBC-SHA256 and CBC-SHA384 names, the Conscrypt-only RSA-key-exchange GCM names); M-X2 is replaced by M-X3 (blocked list emptied); AC-10 needs no rewording (C1 to C3 stay true) and its step S0-2 does not apply; the "Not stated" bullet on names on neither list stays, and AC-3 must say in Implementation Notes that "nothing weak is enabled" holds only over the names the tests can see.

### DP-3: the failed-initialisation branch for cipher suites (CR-014 Scope Concern A)

Today a null cipher list (the provider query threw when the class was first used, `:119-125`) leaves the platform's suites: `if (ciphers != null)` at `:237-239`, so the blocked list is not applied. U-065 closed the protocol side (`:240`: the list is computed from the socket itself). Options: **(1, recommended)** compute the cipher list from the socket's own default-enabled suites in that branch, as U-065 did for protocols; then CR-014's prepared statement C4 ("C1 to C3 hold on every socket a producer returns, also when the producer could not work out its suite list in advance: either they hold on the socket, or `createSocket(...)` returns no socket.") can be applied. **(2)** leave it and say why (no supported platform is known to produce the failure; CR-014 keeps the "Not stated" bullet).
Recommendation: **(1)**. Reason: it is the same few lines as the protocol side, it sits in the step this story edits anyway, and it removes the one path on which the pruned list would silently not apply. A real initialiser failure cannot be forced in a test (it runs once per class loader; U-065 AC-1 (e)), so the branch's code is called directly. If the platform throws while the step reads the socket's suites, the exception leaves `createSocket` and no socket is returned (fail closed, as for protocols; U-065 Implementation Notes).
If (2) is ruled: AC-4 becomes "Implementation Notes record the reason; `hardenSocket_withNullLists_stillAppliesTheProtocolFloorFromTheSocket` is unchanged, including its `never()` check on the suites (`DefaultTrustedSocketFactoryHardeningTest.java:522`); C4 is not added"; mutation M-X7 is dropped.

### DP-4: provider-fixed suites, suites named on neither list, and order

- **Provider-fixed suites.** Under Conscrypt the three TLS13 suites are reported enabled whatever the caller sets and come first in the provider's own order `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384`, `TLS_CHACHA20_POLY1305_SHA256` (`I0-probe.txt:31` against `:32`; the existing test measures them live, `DefaultTrustedSocketFactoryHardeningTest.java:580-606`). Under the JDK provider they are ordinary entries and keep the order the factory gives (`I0c-diag.txt:16`). Recommended: TLS13 are on the allowed list, first, in Conscrypt's own order, so both providers report the same order; an allow-list that omitted them would leave TLS 1.3 enabled with no TLS 1.3 suite under the JDK provider (assumed from CR-014 point 10, not measured; step S0-4 measures it).
- **SCSV.** It is in both providers' default lists (`I0-probe.txt:30`, `I0c-diag.txt:14`) and is not a cipher. Recommended: stays on the allowed list, last, so the story changes nothing about renegotiation signalling (whether the app needs it is not measured; keeping it is the no-change choice). Weak-suite checks (AC-3) exempt exactly this name and say so.
- **Suites named on neither list today.** Under the allow-list: dropped unless on the allowed list. Present in the test providers' defaults and dropped: Conscrypt `TLS_RSA_WITH_AES_128_GCM_SHA256`, `TLS_RSA_WITH_AES_256_GCM_SHA384`; JDK `TLS_DHE_RSA_WITH_CHACHA20_POLY1305_SHA256`, `TLS_DHE_DSS_WITH_AES_{128,256}_GCM_SHA{256,384}`, and the eight `_CBC_SHA256` and `_CBC_SHA384` suites. Kept although on neither list today: the two ECDHE ChaCha20 TLS 1.2 suites (they join the preferred order).
- **Order.** Today: strength first, RSA before ECDSA at each strength: `ECDHE_RSA_AES256_GCM`, `ECDHE_ECDSA_AES256_GCM`, `ECDHE_RSA_AES128_GCM`, `ECDHE_ECDSA_AES128_GCM` (`:38-41`); ChaCha20 is on neither list and so follows in the platform's order. Order matters only when the server honours the client's preference and has several suites in common; the certificate's key type already limits the choice, and every suite left is authenticated encryption with forward secrecy, so no choice among them is a security difference (a reasoning, not a measurement). Recommended: TLS13 first, then today's four in today's order, then `ECDHE_RSA_CHACHA20` and `ECDHE_ECDSA_CHACHA20`, then SCSV. Resulting list L-A, which both providers must report for option A:
  1 `TLS_AES_128_GCM_SHA256`, 2 `TLS_AES_256_GCM_SHA384`, 3 `TLS_CHACHA20_POLY1305_SHA256`, 4 `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384`, 5 `TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384`, 6 `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`, 7 `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`, 8 `TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305_SHA256`, 9 `TLS_ECDHE_ECDSA_WITH_CHACHA20_POLY1305_SHA256`, 10 `TLS_EMPTY_RENEGOTIATION_INFO_SCSV`.
  The set is verified from the recorded defaults; the order (JDK keeps the order set, Conscrypt puts TLS13 first in the same order) is derived from `I0-probe.txt:31` and `I0c-diag.txt:16` and is confirmed by step S0-4 before any assertion is written. For B the list is L-A with the four CBC12 names, in the order `ECDHE_RSA_AES256_CBC_SHA`, `ECDHE_ECDSA_AES256_CBC_SHA`, `ECDHE_RSA_AES128_CBC_SHA`, `ECDHE_ECDSA_AES128_CBC_SHA`, inserted before SCSV (14 names).
If another order is ruled: only the order in AC-1, AC-2 and M-X8 changes. The existing non-vacuity precondition (the factory's order must differ from the provider's own, `assertCipherOrderIsNotTheProviders`, `PinnedCertificateSocketFactoryCreateSocketTest.java:365`, and `DefaultTrustedSocketFactoryJdkProviderTest.java:499-502`) must still hold: a ruled order equal to a provider's own would make the parity tests pass without the factory, and is reported to the orchestrator.
