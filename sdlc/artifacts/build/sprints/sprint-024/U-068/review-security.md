# Security Review: U-068

## Review Summary

Story U-068 raises `minSdkVersion` from 21 to 24 (`app/build.gradle:24`), removes two permission declarations that were capped below API 24, removes seven dead version branches, prunes eleven stale lint-baseline entries, switches on JUnit XML reports, and adds or retargets tests. I read the seven increment commits (`533e9f51` to `0d490997`) with `git show` and `git diff 4300ffa9 0d490997`, not the working tree, plus the committed evidence folder. No blocking issue was found. The change removes code that could only run below API 24 and removes permissions that the platform never grants at 24 and above; nothing at API 24 or higher executed a different security-relevant path before and after. The set of exported components, their permissions, the backup rules and the network security config are identical before and after. Four Low findings and several Info items remain; none must be fixed in this cycle.

Verified against the committed code and evidence, not the implementation log's descriptions:

- `git diff 4300ffa9 0d490997 --name-only` outside `sdlc/` lists 18 files: the manifest, `app/build.gradle`, `build.gradle`, `app/lint-baseline.xml`, `CHANGES`, `DEVELOPMENT.md`, one issue template, eight production source files and three test files. `gradle/` (including `verification-metadata.xml`), `gradlew*`, `settings.gradle`, `gradle.properties`, `.github/workflows`, `app/proguard-rules.pro` and `k9mail-vendored/` are absent from the diff.
- The `app/build.gradle` diff is three lines of comment text plus `minSdkVersion 24`; no dependency line moved. `build.gradle` changes one line, `reports.junitXml.required = true`.

### Warnings

Classification follows `knowledge/standards/review-finding-classification.md`.

- **W-1 (Low). The Android 7.0 test runtime jar was fetched by the test framework outside Gradle dependency verification (`gradle/verification-metadata.xml` does not cover it).** Acknowledged by ruling P-1 and design D5. What the record gives: coordinates `org.robolectric:android-all-instrumented:7.0.0_r1-robolectric-r1-i7`, jar 88,212,080 bytes and pom 1,403 bytes, each with a SHA-512 that the evidence shows equal to the `.sha512` file served beside it (`evidence/I3-sdk24-jar.txt`); the folder did not exist before the first run and both build-file checks (uncommitted and against the start commit) returned 0 before and after, so no build file, `robolectric.properties` or verification metadata changed. What it does not give: the `.sha512` file comes from the same server as the jar, so the match shows the transfer is intact, not who published it, and it is not pinned to a value fixed in the repository. The jar is a test-classpath artefact only (`testImplementation`); it is not in either APK (`so=0`, class-file majors unchanged, kept names and R8 configuration identical per `I4-apk-diffs.txt`). The practical exposure is the developer machine running a tampered test runtime; a test-time-only risk, shared with every other SDK level the project's tests already use (the same resolver fetched those). I checked that nothing was fetched by hand: the log records no manual download. — Classification: defer-justified — test-only, pre-accepted by P-1, same trust model as the existing Robolectric SDK jars; pinning the jar would need a project-wide Robolectric offline-mirror decision that is its own story.

- **W-2 (Low). Dead pre-24 branches remain in the vendored mail library and are now unreachable.** `k9mail-vendored/.../DefaultTrustedSocketFactory.java:201-206` (`SDK_INT >= ICE_CREAM_SANDWICH`, always true), `:248-257` (the `setSniHost` `else if` and reflective `setHostnameViaReflection` paths, never taken at 24 and above), and `KeyChainKeyManager.java:105` (`< JELLY_BEAN_MR1`, never true). They are not a vulnerability: at 24 and above `setSniHost` always takes the public `SSLParameters` path (`:248-249`), which is the path already used on every device that runs the app today. The story deliberately left `k9mail-vendored/` untouched (AC-9, AC-12). The cost is a reader seeing a fallback that cannot run, and a reflective path that would be the weaker one if it ever did. — Classification: defer-justified — outside the story's allowed file list; the follow-up belongs with the vendored-library clean-up and has no runtime effect.

- **W-3 (Low). The debug APK carries only an APK Signature Scheme v2 signature, and no document says so.** At minSdk 24 AGP stops writing the v1 JAR signature (`META-INF/CERT.RSA`, `CERT.SF`, `MANIFEST.MF` are absent from the debug APK; `apksigner verify -v` on the I4 debug APK reports Verifies, v1 false, v2 true, `implementation-log.md` I4 entry). See item 3 under "Assessment" for why this is safe on all supported levels. The release signing config (`app/build.gradle:32-37, 55`) names no signature-scheme flags and so follows the AGP default (v1 off, v2 and v3 on at this floor); the release APK in the evidence is unsigned because no keystore is present in the workspace, so a signed release was not inspected. No CI, workflow or document in the diff or at HEAD mentions v1. One edge: a tool or process that checks the JAR manifest of the APK (for example a repackager) would no longer find one. — Classification: defer-justified — private app installed by its owner on API 24 and above; the owner's device update check (orchestrator IC-3/IC-4) covers the install path, and a signed release, if ever built, should be verified with `apksigner` at that time.

- **W-4 (Low). The pre-Q default-SMS-app branch has no unit test, and the retained pre-Q path in `SmsDefaultRoleHelper.startRestore` now covers API 24 to 28 only.** The `_belowQ` cases (M-R2 proves them) were added or retargeted to API 24 in `SmsReceiverTest` and `SmsDefaultRoleHelper`-level tests; the implementation log notes that the pre-Q package-and-dialog path in `startRestore` has no test (pre-existing gap, plan section 7). The code path is a straight deletion of the outer `>= KITKAT` guard plus an unindent, with the body unchanged (`git diff -w`: five lines removed, none added). — Classification: defer-justified — pre-existing gap, behaviour unchanged at every supported level; recorded by the developer for a later story.

### Info

- **I-1. Manifest permissions (assessment item 1).** `USE_CREDENTIALS` (`maxSdkVersion 22`) and `WRITE_EXTERNAL_STORAGE` (`maxSdkVersion 18`) are removed (`app/src/main/AndroidManifest.xml`, hunk `@@ -38,14 +37,0 @@`). Both were already absent from the merged manifest of any device at API 24 and above because `maxSdkVersion` filters them at install. `USE_CREDENTIALS` has been ignored since API 23 (AccountManager token access moved to the account-visibility model); the app keeps `GET_ACCOUNTS` (unchanged line 36). `WRITE_EXTERNAL_STORAGE` at 24 and above would have been neither declared nor granted, and the app writes only to its own app-specific directories. The merged-manifest comparison I0 against I7 (`git diff --no-index`, 2 insertions and 19 deletions per variant) shows exactly three kinds of change: `minSdkVersion` 21 to 24, the two permission blocks, and `extractNativeLibs` true to false. The removed lines also include their comments; no other permission, `uses-feature`, component, `intent-filter` or attribute differs.
- **I-2. Attack surface before and after (assessment item 1).** Exported components in the merged release manifest, identical at I0 and I7 (line order shifts by the 17 removed lines only):
  - Activities: `MainActivity` (launcher, exported true); `RedirectReceiverActivity` (exported true, VIEW and BROWSABLE for the OAuth redirect); `ComposeSmsActivity` (exported true, SEND and SENDTO).
  - Receivers: `BackupBroadcastReceiver` (exported true, action `com.zegoggles.smssync.BACKUP`, no permission; guarded in code by the opt-in check, now unit-tested in `BackupBroadcastReceiverTest`); `SmsReceiver` (exported true, protected by `BROADCAST_SMS`); `MmsReceiver` (exported true, protected by `BROADCAST_WAP_PUSH`).
  - Services: `HeadlessSmsSendService` (exported true, protected by `SEND_RESPOND_VIA_MESSAGE`); WorkManager's `SystemJobService` (exported true, protected by `BIND_JOB_SERVICE`).
  - Not exported: `SmsBroadcastReceiver` (also `BROADCAST_SMS`), `BootReceiver`, `PackageReplacedReceiver`, `SystemForegroundService`, `SystemAlarmService` and the WorkManager constraint proxies.
  `allowBackup="true"`, `fullBackupContent="@xml/backup_descriptor"`, `networkSecurityConfig="@xml/network_security_config"` and the custom dynamic-receiver permission are identical in both manifests, and `app/src/main/res/xml/` is not in the diff. No `debuggable` attribute is present in the release manifest in either. The set grows by zero and shrinks by zero.
- **I-3. `extractNativeLibs` true to false (assessment item 1).** This is the AGP default behaviour change at minSdk 24 or higher (native libraries are mapped from the APK rather than extracted). The APK has no native library (`so=0` in both the I0 and I4 comparisons), so nothing is mapped or extracted. It has no effect on the attack surface, exported components or permissions. For apps that do ship libraries it avoids a world-readable-by-owner on-disk copy; here it is moot.
- **I-4. The seven removed branches (assessment item 2).** Each removed condition traced for API 24, 29 and 36:
  - `SmsReceiver.isDefaultSmsApp` (`compat/SmsReceiver.java:45-51`): before, `Q and above` used `RoleManager.isRoleHeld(ROLE_SMS)`, `KITKAT to P` used `context.getPackageName().equals(Sms.getDefaultSmsPackage(context))`, below KITKAT returned `false`. After, `Q and above` unchanged; everything else uses the package-equals check. API 24 and 29 (29 is Q): same code before and after. API 36: role check, same. Only the unreachable `return false` below API 19 is gone, which was the fail-closed default for a platform without the concept; no supported level has it. The `onReceive` guard that gates all processing on this result is untouched (`:35`).
  - `SmsDefaultRoleHelper.startRestore` (`activity/SmsDefaultRoleHelper.kt:74-97`): before, the whole body sat in `SDK_INT >= KITKAT` and the else called `startViewModelRestore()` unconditionally (restore with no default-app check, pre-KitKat). After, the check is unconditional: default app then restore; Q and above then request the role (dialog first time); otherwise the legacy package path. At 24 (legacy path), 29 and 36 (role path) the executed statements are identical to before. The removed `else` was the only path that skipped the default-app requirement and is unreachable at 21 and above, so no supported level bypassed it.
  - `MainActivity.startRestore`: only `@TargetApi(KITKAT)` removed (lint annotation, no bytecode). `Dialogs.About.onPageFinished`: operand `SDK_INT >= ICE_CREAM_SANDWICH` (always true at 21 and above) removed; scroll position restoration only, no security role. `CalendarAccessorPost40`: `@TargetApi(ICE_CREAM_SANDWICH)` only. `App.java` and `BackupScheduler.java`: comment and javadoc text only.
  - `WorkManagerScheduler.scheduleContentTrigger`: before, `SDK_INT < N` returned `null` (no trigger; the broadcast path covered it); the encryption-degraded guard before it (`:219-222`, returns `null`, plaintext-credentials block from U-054) is unchanged and still first. At 24, 29 and 36 the `< N` test was false before, so the trigger registration ran; it runs the same way after. The `SmsBroadcastReceiver` fallback is not removed and not relied on at 24 and above.
  - None of the seven was a permission check, a signature or caller check, or a TLS or credential path. The one default-app check (`SmsReceiver`, `SmsDefaultRoleHelper`) is unchanged at 24 and above.
- **I-5. Signing and installation (assessment item 3).** APK Signature Scheme v2 was introduced in Android 7.0 (API 24), the new floor. Every supported level verifies v2 natively and checks it in preference to any v1 signature, so install, update and the same-key check for in-place update work on 24, 29 and 36 exactly as for a v1+v2 APK signed with the same key. The debug build is signed with the debug key, the same key as before; only the extra JAR signature is gone. An existing installation signed with v1+v2 updates to a v2-only APK with the same certificate. What would not work, and is correctly gone with the floor, is installing on API 21 to 23, where only v1 is read and a v2-only APK reports "no certificates". A downgrade of an existing install is not a signing concern here. Release signing config, CI workflow and documents assumed no scheme: `app/build.gradle:32-37, 55` takes values from an untracked `keystore.properties`, and `grep` of the committed workflows and documents for v1, jarsigner and apksigner gives nothing. The unsigned release APK never had `META-INF/CERT.*`.
- **I-6. The floor itself (assessment item 4).** Dropping 5.0 to 6.0 removes platforms where the app's TLS and key-storage behaviour was weaker or different, and no supported behaviour changes:
  - TLS: the app's own TLS policy lives in `k9mail-vendored/.../DefaultTrustedSocketFactory.java` (`ALLOWED_PROTOCOLS` TLS 1.2 and 1.3 at `:80-83`, `hardenSocket` at `:243-246`) and `app/.../mail/PinnedCertificateSocketFactory.java:89`; both apply the allow-list on top of whatever the platform offers, so U-065 and U-066 are unaffected. The platform defaults at 21 to 23 (TLS 1.1 and 1.2 off by default on 5.0) are what that code existed to fix; at 24 and above the platform enables TLS 1.2 by default and the allow-list is a narrowing. Nothing in the app depended on a 21 to 23 default.
  - Keystore and `security-crypto`: `androidx.security:security-crypto:1.1.0` (`app/build.gradle:147`) backs `EncryptedPrefsSecretStore` with an AES-256-GCM master key in the Android Keystore. The library's own requirement is API 23; keys generated at API 23 and above have the full `KeyGenParameterSpec` and AES-GCM support, so 21 and 22 were already unsupported for the encryption in practice and a degraded-encryption fallback exists (U-054 guard above). At 24 and above there is no change to how the master key is created or read; no stored data format changes. No code in `app/src/main` branched on `SDK_INT` for keystore or cipher choices (grep of `SDK_INT` in `app/src/main` returns only `Q`, `O`, `TIRAMISU` and 26 comparisons).
  - Workarounds for old weaknesses: none found in `app/src/main`. The only sub-24 security-adjacent leftovers are the vendored-library branches in W-2.
