# U-070: Back Up an SMS That Becomes Visible to the App After Later Messages Were Backed Up, Exactly Once, With a 6-Hour Look-Back Below the Watermark and a Local Record of What Was Uploaded

## Story
As the owner of this private, unpublished SMS Backup+ build (its only user; on an Android 17 phone the platform can hand the app a text message up to three hours after it arrived, with its original date),
I want every SMS that the app can see to be backed up to Gmail exactly once, including one that becomes visible after newer messages have already been backed up,
So that no message is silently and permanently missing from the backup because the backup had already moved past its date, and so that the story that raises `targetSdkVersion` to 37 is no longer blocked by this gap.

Source: defect BUG-021 (`sdlc/artifacts/stories/BUG-021-delayed-otp-sms-skipped-by-backup-watermark.md`, status ready) and the requirement it serves, REQ-MODERNIZATION-020 (`sdlc/artifacts/requirements/modernization/REQ-MODERNIZATION-020-backup-completeness-for-late-visible-messages.md`, approved, 25 criteria, look-back bound W = 6 hours, amended by CR-016, cross-references only). The librarian attaches REQ-MODERNIZATION-020 to this story's `requirements` field after this text is approved; the story implements every criterion of it except AC-25 (see "Not this story's"). Where BUG-021's criteria and the requirement differ, the requirement governs (BUG-021 AC-1, AC-6, AC-7). The design that sequences the work is `sdlc/artifacts/design/modernization/DES-MODERNIZATION-014-toolchain-runtime-libraries-platform-level-design.md`, decision D14 and slice S5; the orchestrator's rulings are Record 13 row 4 and Record 14 rows 10 and 11 of the appendix "Product owner decision" in `sdlc/artifacts/build/feasibility/U-062/thunderbird-mail-libraries-feasibility-analysis.md`.

Out of scope: the Android 17 measurement S5-I1 (Runs A, T and R) and the device check of the fixed build on an API 37 emulator, which REQ-MODERNIZATION-020 AC-25 and BUG-021 AC-12 name (they belong to the targetSdk 37 story and its QA step, "Not this story's" below); raising `targetSdkVersion`; MMS and call-log late rows (DP-2); recovering messages the app already skipped before this fix; any change to the `MailTransport` port, the mail library, the manifest or a dependency; the incoming-backup enqueue path (U-069); the worker cancellation checks (U-067); any user interface beyond two README sentences.

Terms (the vocabulary of REQ-MODERNIZATION-020). **Watermark**: the stored SMS `max_synced_date` (`DataTypePreferences.java:59-70`). **W**: the look-back bound, 21,600,000 ms. **Window**: SMS rows with `watermark - W < date <= watermark`. **Forward rows**: rows with `date > watermark`. **Late-visible SMS**: one that becomes visible to the app with `date <= watermark`. **Record**: the local bookkeeping of which window rows were uploaded or examined (REQ-020 calls it "bookkeeping"). **Provider double**: the test-local SMS provider described next. **Recording transport**: a test double of `MailTransport` that records, for every `appendMessages`, the message's `Message-ID` and `X-smssync-id` headers and the provider row it came from, and counts every port call.

Test fixtures every criterion relies on (new, test-only; no production file, no dependency):
- **Provider double.** A `ContentProvider` registered with `ShadowContentResolver.registerProviderInternal` like `FakeSmsContentProvider` (`app/src/test/java/com/zegoggles/smssync/service/RestoreWorkerCheckpointTest.kt:512-570`), which cannot be reused as it stands because its selection matching serves restore's duplicate check only (`:553-556`). The new one (i) evaluates exactly the selection texts the code emits (`date > ?`, `date <= ?`, `type <> ?`, `AND (type = 2 OR person IN (...))`, and restore's `date = ? AND address = ? AND type = ?`) against rows holding `_id, date, address, body, type, person, read, thread_id`; (ii) honours the sort `date` and `LIMIT n`; (iii) throws on any selection text it does not recognise, so a changed query shape fails the test instead of silently returning every row; (iv) records every query it receives and every row it returns; (v) can add a row, change a row's `type`, hide a row (not returned until released, which models Android 17's withholding as the app sees it) and store a row then throw from `insert` (a process death after the insert); (vi) serves restore's `insert`. Whether an in-memory SQLite database behind the provider works under this project's Robolectric mode (4.15.1, `app/build.gradle:160`) was not tried; the hand-written evaluator is the assumed route and the plan may use SQLite if it works.
- **Dates.** Fixed epoch-millisecond values, as `BackupWorkerWatermarkTest.kt:63-64` does. The selection uses the watermark, never the wall clock, so there is no clock to control; `X-smssync-backup-time` (`HeaderGenerator.java:53`) is the only wall-clock value and is excluded from every comparison.
- **Real collaborators.** Real `DataTypePreferences` over Robolectric's preferences, real `BackupQueryBuilder`, `BackupItemsFetcher`, `BulkFetcher`, `BackupCursors` and `MessageConverter`; the backup is driven through `BackupWorker` with `TestableBackupWorkerFactoryWithTransport` (`BackupWorkerIntegrationTest.kt:86-`) or, if the real converter cannot run over the provider double under Robolectric (not verified; `MessageConverterTest.java` is the model), through the fetch layer and `backupCursors`, which U-067 makes `internal`. The plan reports to the orchestrator before any production edit if neither works; no criterion is weakened.

## Acceptance Criteria

Each criterion names the REQ-MODERNIZATION-020 criterion (REQ AC-n) and BUG-021 criterion (BUG AC-n) it carries. All 25 criteria of the requirement are mapped: AC-1 to AC-24 to the criteria below, AC-25 to "Not this story's".

- [ ] AC-1 (a late-visible SMS is uploaded; REQ AC-1 first part, BUG AC-1 and AC-9): Given message B (date 2000, inbox) was uploaded and the SMS watermark is 2000, when message A (date 1000, inbox) is then added to the provider and the next backup runs, then that backup uploads A exactly once, does not upload B again, and leaves the watermark at 2000. The same holds when other backups ran in between before A became visible, and when A becomes visible after any number of runs (the selection is relative to the watermark, so how late the backup runs does not matter). This test is written first and shown failing on the start commit (the provider double's record shows the selection `date > 2000 AND type <> 3` and A not uploaded; the output is kept in the story's evidence folder with the commit id), then passing after the change; it is not `@Ignore`d.
- [ ] AC-2 (the per-run item limit, nothing starved; REQ AC-1 second part and AC-22, BUG AC-7): Given a per-run limit of N, then (a) with N + 1 late-visible SMS waiting, the first backup uploads N and the following backup uploads the last one, none lost because of the limit; (b) a late-visible SMS that a run uploads counts against N like any other row, so the MMS and call-log queries of the same run receive a smaller budget by exactly that number (`BulkFetcher.java:23-33`); (c) with limit N, at least N SMS already backed up and dated within W below the watermark, one late-visible SMS and N SMS dated above the watermark, the run uploads N items with the late-visible SMS among them, uploads none of the already-backed-up SMS, and the next run uploads the remaining forward SMS; the already-backed-up window rows are not counted against N. Late-visible rows are uploaded before forward rows, in ascending `date` order within each group.
- [ ] AC-3 (same selection rules; REQ AC-2): Given one late draft (`type` 3) and one late message outside the contact group the user chose (the group clause of `BackupQueryBuilder.java:149-163`), when the backup runs, then neither is uploaded; a late message inside the group is uploaded. The window query carries the same draft exclusion and the same group clause as the forward query.
- [ ] AC-4 (W is one named value; REQ AC-3, BUG AC-2): W is defined once in production code as a named constant equal to 21,600,000 ms, with a comment giving its derivation (the platform's three hours plus three hours of margin for release-time jitter and clock differences, neither measured), why it is measured against the watermark and not against the time the backup runs (the watermark cannot pass a withheld message's release time before a backup has seen the message, so a backup that runs late still reaches it), that S5-I1 Run T is the only evidence of the delay's length and that a longer delay revisits W by change record. The window query, the record's pruning, the Skip and upgrade seeding and the restore write all read that one constant. `git grep -n -E "21600000|21_600_000|6 \* 60 \* 60" -- app/src/main` shows the one definition.
- [ ] AC-5 (the boundary, and what is not promised; REQ AC-4 and AC-5 first sentence, BUG AC-2): Given a message that becomes visible with its date W minus 1 ms below the watermark, when the next backup that completes without error runs, then it is uploaded (boundary test). A message dated exactly W below the watermark is not returned to the backup by the provider (the selection bound is exclusive); no test requires such a message, or one older, to be uploaded.
- [ ] AC-6 (nothing changes when nothing is late; REQ AC-6 and AC-24, BUG AC-10): Given a provider in which no row ever becomes visible at or below the watermark, when a sequence of backups runs over in-order rows, then it uploads the same messages in the same order, with the same headers apart from `X-smssync-backup-time` and, if the version code changes, `X-smssync-version`, to the same folder, and leaves the same watermark after each run as the code before the change. The expected sequence is a literal list recorded by running the test body on the start commit (output kept in the evidence folder), not recomputed from new code. `BackupWorkerWatermarkTest.kt`, `BackupWorkerIntegrationTest.kt` and `BackupQueryBuilderTest.java` (all eight tests, including the forward SMS selection `date > ? AND type <> ?` at `:38-40` and `:51-53`) pass without edits, so the signature of `appendBatchAndUpdateWatermark` (`BackupWorker.kt:404-409`) is frozen and the forward query text is unchanged.
- [ ] AC-7 (no row stored twice across runs; REQ AC-7, BUG AC-3): Given three or more consecutive uninterrupted backups over a provider that keeps its rows and receives a late-visible row between runs, and at least one row that was uploaded in an earlier run and is dated within W below the watermark, then no provider row is appended more than once, and no `Message-ID`, no `X-smssync-id` and no (date, address, body) triple occurs twice in the recording transport's list across all runs.
- [ ] AC-8 (a row whose type changes is not uploaded again; REQ AC-8): Given a row uploaded as outbox (type 4) whose `type` the provider then changes to sent (2) with its date unchanged and within W below the watermark, when the next backup runs, then it is not appended a second time (the `Message-ID` includes the type, `HeaderGenerator.java:50`, `:108-128`, so a key that included the type would upload it twice).
- [ ] AC-9 (no state change without a confirmed append; REQ AC-9 and AC-11, BUG AC-10): Given an interruption or failure at each point from "append requested" to "state saved" that precedes the server's confirmation (folder open throws, append throws, login fails, cancellation), when the next backup runs, then neither the watermark nor the record has changed for that row and the row is uploaded; no row the server did not confirm is ever treated as backed up. `BackupWorkerWatermarkTest.kt` passes without edits.
- [ ] AC-10 (an interruption after the server's confirmation; REQ AC-10 and AC-11, BUG AC-3 last sentence): Given the transport records the append and the process then dies before the state is saved (the recording transport records the message and then throws), when the next backup runs, then it may append that one message again (accepted, as today), no other message is appended twice, and a further backup appends none of them. The watermark and the record for a row are written in one `commit()` (a counting wrapper around the preferences shows one commit per uploaded row that carries both), so no crash can leave the watermark advanced and the record behind, or the reverse; the crash window is the one that exists today and is no wider.
- [ ] AC-11 (the watermark never moves backwards; REQ AC-12, BUG AC-4 and IC-1): Given a backup that uploads only a late-visible row dated below the stored SMS watermark, then the stored watermark afterwards is equal to or higher than before; a result with no parseable date (`ConversionResult.getMaxDate()` is -1, `ConversionResult.java:13`) leaves it unchanged. The guard applies to SMS only: for MMS and call log the write stays as today and the MMS seconds-against-milliseconds handling (`DataTypePreferences.java:59-66`) is not touched. Skip and the first-run sentinel still set the value outright (`BackupWorker.kt:207`, `:259-260`). `AdvancedSettings.java:230` and `StatusPreference.java:370` are unchanged (`git diff`), and the "last sync" values shown are still read from the stored watermarks.
- [ ] AC-12 (Skip; REQ AC-13 and AC-14, BUG AC-5 ii, decision DP-3): Skip connects to no server and uploads nothing (`BackupWorker.kt:198-218`, the transport double throws on any call). (a) Every SMS visible to the app at Skip time, whatever its date relative to the new watermark, is not uploaded by any later backup until a Reset or account removal: a test skips over rows dated W or more below the new watermark and rows dated within W below it, runs a backup, and asserts nothing is uploaded. (b) An SMS that exists in the provider but is hidden from the app at Skip time and becomes visible later with its date less than W below the watermark is uploaded by the first backup after it became visible (the provider double hides it at Skip, releases it afterwards). Skip over a type set that does not contain SMS leaves the SMS watermark and the record untouched.
- [ ] AC-13 (Reset and account removal; REQ AC-15, BUG AC-5 iii): Given backups that have run and a late-visible row, when the settings are reset or the account is removed (`clearLastSyncData`, called at `MainSettings.java:82` and `:94`), then `Preferences.isFirstBackup()` is true, nothing left from earlier backups suppresses any SMS, choosing Backup uploads every visible SMS once (more than one backup when the per-run limit is smaller than the number of SMS), and a further backup uploads none of them again; choosing Skip then applies AC-12.
- [ ] AC-14 (restore; REQ AC-16, BUG AC-5 i): Given a restore that inserts SMS, then (a) a later backup uploads none of the SMS the restore inserted, including a row dated within W below the watermark and a row dated above the watermark; (b) when the process dies after the row is inserted and before the watermark is raised (the provider double stores the row and throws from `insert`), the next backup still does not upload that row; (c) a late-visible row added before the restore, with a restored row dated 2 hours above it (so the restore raises the watermark by 2 hours), is uploaded by the next backup; (d) the restore's own check for messages already on the phone (`RestoreWorker.kt:599-617`, `date = ? AND address = ? AND type = ?`) and its watermark update (`:464-468`, raised only when higher, after the insert) are unchanged, shown by `RestoreWorkerIntegrationTest.kt` and `RestoreWorkerCheckpointTest.kt` passing without edits. This is stricter than today on purpose (REQ AC-16).
- [ ] AC-15 (first run; REQ AC-17): Given no watermark (the first run after installation), then behaviour is identical to today: every visible SMS is selected subject to the per-run limit and uploaded once; when the first run finds nothing the sentinel -1 is written to the SMS and MMS watermarks (`BackupWorker.kt:257-261`); the app stays in its first run until a watermark exists (`Preferences.java:220-227`, which reads only the three watermark keys, so the record's keys never make `isFirstBackup()` false); no look-back query is sent while the watermark is -1. The existing first-run tests pass without edits.
- [ ] AC-16 (upgrade from the version before this change; REQ AC-18, BUG AC-6): Given a stored SMS watermark and no record (an upgrade), when the first backup after the upgrade runs over rows both below and above the watermark inside W, then it uploads no SMS that is visible at its start with a date at or below the watermark, and uploads every SMS dated above the watermark as before; an SMS released between the upgrade and that first backup, dated at or below the watermark, is therefore not uploaded (today's outcome); an SMS that becomes visible after that first backup is uploaded as AC-1 says. The test asserts the exact list of rows uploaded, written as a literal. Messages the earlier version lost stay lost (out of scope). The story states in Implementation Notes how the empty record is treated and why (Technical Context, "Upgrade").
- [ ] AC-17 (Android's own app backup to another phone; REQ AC-19): Given the files that `app/src/main/res/xml/backup_descriptor.xml` lets Android copy (the test parses that resource, so the excluded names are not hard-coded) copied to a fresh store, over a provider holding the same messages under new row ids, then the first backup there uploads nothing dated at or below the restored watermark; and when the new provider also holds an SMS dated within W below the restored watermark that the old phone never uploaded, that SMS is uploaded. The record lives in the default preferences file next to the watermark (`AndroidManifest.xml:95-96`: `allowBackup="true"`), not in a file the descriptor excludes. A duplicate is accepted, and no test requires one, only where the platform changed a row's date, address or text.
- [ ] AC-18 (MMS and call log unchanged; REQ AC-20, BUG AC-8): The MMS and call-log queries, watermarks (MMS stored in seconds, returned in milliseconds), tests and query code are unchanged: `BackupQueryBuilderTest.java:56-87` passes without edits and `git diff` shows no change to `BackupQueryBuilder.java:118-147`. A late MMS row and a late call-log row dated within W below their watermarks are not selected, shown by the provider double's record of queries, which holds today's MMS and call-log selection texts and no window query for either; an MMS upload leaves the MMS watermark as today (a test would fail if a millisecond value were written into the seconds slot).
- [ ] AC-19 (cost: rows examined and server calls; REQ AC-21, BUG AC-7): The extra SMS rows a backup examines beyond today's are limited to rows dated within W below the watermark at the start of the run: with the provider double recording what it returned, no row dated W or more below the watermark at the start of the run is returned to the backup, and a run sends at most one SMS query beyond today's (the window query; the upgrade seeding of AC-16 and the Skip seeding of AC-12 are one query each, once). The fix adds no server round trip: for a run that uploads n rows the recording transport sees the same calls as the start commit (`checkSettings` once, `openFolder` and `appendMessages` once per uploaded row, `closeFolders` once), no `getMessages`, no `fetch` and no search, and a run that selects nothing makes no transport call.
- [ ] AC-20 (the record is bounded and pruned; REQ AC-23, BUG AC-7 last sentence): The record's size is bounded by the number of SMS dated within W below the watermark (plus rows above it that a restore or the converter-exclusion of AC-21 recorded), not by the age of the install. A test runs 200 backups of 50 SMS each in date order, each group dated more than W after the one before, and asserts the record's entry count and its serialised length after the 200th backup are no larger than after the 2nd. Pruning never causes an SMS dated within W below the watermark to be appended twice or lost: a test with entries at W minus 1 ms and at W below the watermark shows the first still suppresses its row and the second is gone. The story states the largest size it expects, with the reasoning (Technical Context, "Size"). No count cap that could drop an in-window entry exists (Scope Concern 2).

Test: limit N, at least N such rows inside the window and one late-visible genuine SMS; the genuine SMS is uploaded by the run after the rows were examined, and a run that finds only such rows makes no transport call. Such a row is still not uploaded (same selection rules as an in-order message, REQ AC-2).

No log line, exception message or preference value carries a message body or address; the record holds a date and a truncated digest per row and nothing else. A test reads the log lines and the stored record for a row whose body and address are distinctive strings and finds neither string.

### Mechanism (the Solution Architect's recommendation in BUG-021, adopted as the plan's starting point; the plan may replace it if every criterion still holds)

1. **Window.** At the start of an SMS fetch with watermark `D1 > 0`, query `date > D1 - W AND date <= D1 AND type <> 3` plus the group clause, sorted by `date`, with no SQL `LIMIT`; drop rows whose (date, digest) is in the record; keep the first `budget` rows when a limit applies (so a window full of already-uploaded rows cannot fill a `LIMIT` and starve a late row); the remaining budget goes to the forward query, which is the existing one. Late rows precede forward rows because their dates are at or below `D1`. When `D1` is -1 no window query is sent.
2. **Key.** A row is identified by its date and the first 16 hex characters of SHA-256 over date, address and body (an empty address counts as empty text). Not the type (AC-8), not the provider `_id` (restore and Android's backup change it, AC-14, AC-17). Two rows share a key only with the same millisecond, address and text; the result of a changed address or text is a duplicate, not a loss, which DP-5 accepts.
3. **Record.** One string preference beside `max_synced_date`, one `date:digest` per line, plus an integer version marker, in the default preferences file so that it travels with the watermark. Every write that adds entries also prunes entries dated at or below `max(stored watermark, new watermark) - W`.
4. **Single commit.** After a confirmed append, for SMS: new watermark = `max(stored raw, confirmed)`; entries for the uploaded rows are added; the record is pruned; marker, watermark and record are written in one `commit()`. A static or shared lock covers the read-modify-write so two `DataTypePreferences` instances over the same preferences cannot lose an entry (whether two backup workers can overlap was not examined, Scope Concern 9).
5. **Skip.** After setting the watermark, seed the record with every visible non-draft SMS in `(new watermark - W, new watermark]` (no group clause) and write the marker. A message hidden at Skip time is not in the seed, so it is uploaded when released, which is DP-3.
6. **Upgrade.** If the marker is absent and the watermark is above 0, the first SMS fetch seeds the record with the visible rows in `(watermark - W, watermark]` (union with any entries a restore already wrote) and writes the marker before the window query runs, so nothing visible at that moment is uploaded and an SMS that becomes visible afterwards is. Without seeding, every message of the last W would be uploaded again (REQ AC-18 forbids that); with it, a message the earlier version lost stays lost (out of scope). Restore adds entries but never the marker, so a restore before the first post-upgrade backup does not hide the need to seed.
7. **Restore.** Before each insert, record the row's key when its date is above `max(stored watermark, row date) - W`; the existing raise and checkpoint are untouched. Because that row can be above the watermark after an interruption, the forward rows are also filtered against the record entries above the watermark, and the forward `LIMIT` is widened by their number so filtered rows cannot starve it (zero entries in normal use, so the forward text and the existing tests are unchanged).
8. **Examined rows.** A row that converts to nothing is recorded (record-only write, watermark unchanged) so it is not examined again (AC-21).
9. **Reset.** `clearLastSyncData` removes the record and the marker with the watermarks.

### Size (REQ-020 AC-23: the largest size the story expects, with its reasoning)

An entry is a 13-digit date, a colon, 16 hex characters and a line break: about 31 bytes. Entries are bounded by the SMS rows dated within W below the watermark, plus the few rows above it that a restore or an exclusion recorded. A phone in normal use receives tens of messages in six hours, so the expected size is under 100 entries, about 3 KB. A bulk day of 1,000 messages in six hours is about 31 KB, and a stress case of 5,000 about 155 KB; both are correct, only larger. Each uploaded row already rewrites the whole preferences file with `commit()`; the record adds its size to every such write, which is not measured at the stress case (Scope Concern 8). The first run with thousands of unconvertible rows can hold more entries until the first watermark write prunes them; this is bounded by the number of such rows and is not expected.

### Why the bound is measured against the watermark (REQ-020 Rationale, repeated so a developer need not look)

A backup cannot move the watermark past a withheld message's release time before it has seen the released message, because messages carry receipt-time dates and none is later than the clock. So the first backup after a release has a watermark no later than the release time, which is the message's date plus the delay; W above the delay reaches the message however late that backup runs. A restore can raise the watermark by the dates of the rows it inserts (not guaranteed, AC-5); a future-dated row, from a sender or a clock error, can push it past the clock and shorten the effective window (large skew not examined).

### Limits of the evidence

The provider double is not the platform's provider: it models "hidden until released" as a test input, and nothing here shows that Android 17 hands back a row with its original date (S5-I1 Run A). Android 16 does not withhold messages, so no Android 16 run can show the late-visible path. Whether a crash during `commit()` leaves the old or the new file is taken from the platform's atomic-write behaviour, not tested.
