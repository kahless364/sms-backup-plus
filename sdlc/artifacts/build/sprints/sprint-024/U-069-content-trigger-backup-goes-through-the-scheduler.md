# U-069: Make the Content-Trigger Worker Start the Incoming Backup Through the Scheduler's scheduleIncoming(), So It Obeys the Network, Encryption-Degraded, Auto-Backup and Delay Rules, and Give the Worker Its First Tests

## Story
As the owner of this private, unpublished SMS Backup+ build (its only user, who set "Wi-Fi only" on purpose and whose devices run Android 11 or newer),
I want the backup that an incoming text message starts through the content trigger to be enqueued by the same code that every other incoming backup uses, so that it waits for the network my setting allows and is not started when the app is in the encryption-degraded state, when auto backup is off, or when the incoming delay is 0 or less,
So that automatic incoming backups honour my settings and the security gate decided in U-054, one code path builds every incoming request, and a change to that request in the next stories (BUG-021's fix, the WorkManager upgrade) covers both ways of starting it, with a test that notices if the worker drifts again.

Source: bug BUG-023 (`sdlc/artifacts/stories/BUG-023-content-trigger-backup-skips-scheduling-checks.md`, status ready, severity medium, priority high), fixed by **Route A** as ruled by the Solution Architect (the bug's Suggested Approach, rulings 1 to 7) and by the orchestrator (decision appendix Record 15, rows 15 and 16, in `sdlc/artifacts/build/feasibility/U-062/thunderbird-mail-libraries-feasibility-analysis.md`). There is no REQ-* source; the contract sentence the fix makes true is in CNTR-MODERNIZATION-004 (`sdlc/artifacts/design/contracts/CNTR-MODERNIZATION-004-backup-scheduler.md:384-385`, contract v3). The rulings are binding and are not re-decided here.

**What the fix is, in one paragraph.** `app/src/main/java/com/zegoggles/smssync/worker/BackupTriggerWorker.kt` becomes a Hilt worker in the pattern of `BackupWorker` (`@HiltWorker`, `@AssistedInject constructor`, `BackupWorker.kt:105-116`). It receives the `BackupScheduler` port (and `Preferences`, for its log line) and its `doWork()` logs the same line as today, calls `scheduler.scheduleIncoming()` and returns `Result.success()`. Its own `OneTimeWorkRequest` builder and `enqueueUniqueWork` call are deleted. The class name and package do not change, because work already persisted on the device names the class.

**Not in this story** (each ruled or recorded; none is an acceptance criterion):
- A network constraint or backoff on the content-trigger registration (`scheduleContentTrigger()`). Ruled: none. The contract example at `CNTR-MODERNIZATION-004...md:372-376` that shows one is wrong for WorkManager and is corrected by a later change record that the orchestrator raises; this story edits no contract and no design document (AC-12).
- Cancelling a pending `INCOMING` work when auto backup is switched off (product-owner item PO-1 of the bug; `cancelAll()` is unchanged, AC-11).
- Login and first-backup checks on the trigger path (PO-2; the receiver's own checks, `SmsBroadcastReceiver.java:66-83`, are not copied).
- The SMS-received receiver. The bug establishes from the code that it is not delivered `SMS_RECEIVED` on Android 11 and newer (manifest `exported="false"` and a never-requested `RECEIVE_SMS`); the orchestrator ruled it a defect of its own, left as it is until the owner decides (PO-3, Record 15 row 16). `SmsBroadcastReceiver.java` and its manifest entry show empty diffs (AC-11).
- `BackupWorker.kt`, the `BackupScheduler` port (`BackupScheduler.java:56`), the vendored library, the mail transport.
