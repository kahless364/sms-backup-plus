# U-071: Move the Build Toolchain, the Test Tooling and the CI Action Versions to the Latest Stable Release of Each

## Story
As the owner of this private, unpublished SMS Backup+ build (its only user; every device I use runs Android 11 or newer),
I want the build toolchain (Gradle, the Android Gradle Plugin, Kotlin, KSP, Hilt, androidx.hilt), the test tooling (Robolectric, Mockito, Truth, GreenMail, auto-service, JaCoCo) and the CI action versions moved to the latest stable release of each, one component at a time, with the way they were found to fit together written down and every gate left as strict as it is today,
So that the later stories (compileSdk 37, the runtime libraries, targetSdk 37 and the Thunderbird mail libraries, none of which can compile on today's toolchain) start from a current build, a regression can be traced to one version bump and one commit, and a later upgrade can tell an expected warning from a real defect.

Source: story S2 of the approved design `DES-MODERNIZATION-014` (section "S2 - Build toolchain and test tooling to latest stable", increments S2-I0 to S2-I15; decisions D1, D1a, D3, D5, D7, D8, D9, D17, D18, D19, D10's F-1 stop rule), which carries REQ-MODERNIZATION-015 AC-1 to AC-4 and AC-11 to AC-18. The requirement is as amended by CR-011 (minSdk 24) and CR-016 (AC-13 states the count rule, not a fixed baseline). The story carries S2's scope exactly: S1 is story U-068 (done before this story starts); S3, S4 and S5 are separate stories. The orchestrator's rulings on order are Records 13 to 16 of the appendix "Product owner decision" of `sdlc/artifacts/build/feasibility/U-062/thunderbird-mail-libraries-feasibility-analysis.md`: S2 runs after the BUG-022 fix (story U-067) and after S1 (story U-068), and the S2 step that raises Kotlin re-runs U-067's six mutations, not only its tests (U-067 plan, hand-over item 5, ruled).

Out of scope (each belongs to another story, is held on purpose, or is forbidden):
- S1, minSdk 24 and what it makes dead: story U-068 (this story relies on it, see "What this story relies on").
- S3, compileSdk 35 to 37, the lint-baseline refresh (REQ-MODERNIZATION-017 AC-14 option (a)), the Robolectric default level and the comment in `app/src/test/resources/robolectric.properties`, and CI installing `platforms;android-37.0`: story U-072 (as scaffolded). The one exception is the design's pre-specified move N-6 (AC-8, AC-24), which runs part of S3 inside this story's timeline and is recorded, not decided here.
- S4, the runtime libraries (WorkManager, Lifecycle, coroutines, `androidx.annotation`, `androidx.preference`, `androidx.core:core-role`, `androidx.security:security-crypto`): story U-073 (as scaffolded). JUnit 4.13.2 is S2's row and stays unchanged. No runtime-library version declared in `app/build.gradle` or `k9mail-vendored/build.gradle` changes here.
- S5, targetSdk 37 and the Android 17 behaviour work; BUG-021 (story U-070) and BUG-023 (story U-069) are separate stories.
- `k9mail-vendored/` (design D4b), the JDK (25 stays; the epic forbids moving off it), and every production behaviour. No production source is edited except where a javac `-Werror` warning or the Kotlin 2.4 annotation-target default forces a call-site fix, recorded verbatim (design D3 "javac -Werror rule", Risk 9).
- Overriding transitive versions that nobody declared (Tink, `androidx.core:core`, Conscrypt, BouncyCastle, ByteBuddy; design D1 "not overridden" table); replacing `security-crypto`; pinning the GitHub actions by commit SHA (a recommendation in the design's security section, not required); running Mockito as `-javaagent` (design D7: debt, a follow-up when a JDK in scope refuses dynamic agent loading); fixing the pre-existing `lintDebug` errors (design D17: S3 refreshes the baseline); publishing and rollout (the app is private).

## Bound decisions (recorded here so the plan does not re-decide them)

- One component per increment, each committed on its own with its own verification entries (design S2 preamble; REQ-015 Constraints "Increments"). The increment order is the design's, S2-I1 to S2-I14; the two pre-specified moves are the KSP reorder (AC-7) and the N-6 move (AC-8). Kotlin 2.4 and Hilt 2.60 are separate increments because the coupling goes one way only (Kotlin 2.4 needs Hilt 2.60, Hilt 2.60 is built with Kotlin 2.3.21), so REQ-015's "if they cannot be separated" clause does not apply (design S2-I4).
- The targets are the design's D1 rows owned by S2, re-resolved on the story's planning date by the D1a rule (AC-2). The design's values are the starting set, not a fixed answer: where the design says "newest" the planning date decides, by D1a.
- No Gradle/AGP/Kotlin triple at stable versions is listed as supported by all three vendors. The research's claim that Gradle 9.7.0 + AGP 9.3.1 + KGP 2.4.21 sits inside every published range is **contradicted** (design A17, FD-VAL-004, D3) and is not relied on. The story tries the D1 set first; a warning is debt, never a trigger; a trigger is an error raised from KGP, KSP, the Hilt plugin or AGP (AC-5).
- The fallbacks F1 to F5 are pre-specified in design D3 and carried in AC-5. A failure they do not cover stops the story; the Solution Architect amends the plan; going below today's version or touching the JDK is the product owner's decision.
- Build Tools stays 36.0.0 (AGP 9.5's minimum and default); 37.0.0 would add a `buildToolsVersion` line and a download and no requirement needs it (design D1 row "SDK Build Tools").
- Truth 1.4.5 is included as test tooling although REQ-015's Description does not name it (design D1 row "Truth"; Scope Concern 5). JUnit stays 4.13.2.
- Dependency verification stays on. Each dependency-changing increment follows design D5 (AC-17). No `<trust>` entry, no `verify-metadata` relaxation, no hand-edited checksum, no wholesale regeneration, no hand-deleted stale entry.
- No floor lowered, no `@Ignore`, no test loosened to pass (design D3, D7, D8; REQ-015 AC-13, AC-14). A javac warning that the new toolchain produces is fixed at its call site; `-Werror` is never removed and no `-Xlint:-...` suppression is added (design D3).
- The Robolectric default `sdk=29` and the comment in `robolectric.properties` stay as they are (design D6; the comment is S3-I3). This story adds no test configured below SDK 24.
- Lint is recorded, not gated, in this story (design D17): `:app:lintDebug` was red before JDK 25; rule-ID counts are recorded before and after; `app/lint.xml` and `app/lint-baseline.xml` are not edited.
- Device evidence (AC-17 of the requirement) is split by authority: the launch smoke on `Pixel_9_Pro` is inside the owner's authorisation of 2026-11-20 (IC-4); a manual backup and restore on a device, the API 24 device and the first CI run each need the product owner's decision and are kept apart (IC-5, IC-6). The story does not wait for them.
- Commits: the developer makes the per-increment commits locally, each with explicit paths (never `git add -A`, never `git commit -a`), on `sdlc/modernization-plan`, and does not push; the orchestrator pushes after the reviews. This is **by analogy** with ruling 22 of Record 16 (story U-068); it is an exception to the standing "the developer commits nothing" constraint and is **confirmed** by the orchestrator's ruling before planning (Scope Concern 2; Implementation Notes, "Commits"): one local commit per increment, with the plan's subjects. If the reviews find something to fix, the fix is a further commit; no commit is amended or rewritten.

### Operational lessons (design D16, D18, the U-060 retro; each has a stop rule)

- **Foreground Gradle with long timeouts.** Run every Gradle call in the foreground with an explicit tool timeout above three minutes (600000 ms for the first run after a toolchain change: AGP, Kotlin, KSP and R8 are configured, and Robolectric may download SDK jars). No background shell, no polling.
- **Never `MSYS_NO_PATHCONV=1` for Gradle.** It breaks the wrapper's classpath ("Could not find or load main class org.gradle.wrapper.GradleWrapperMain"). Set it only in adb-only shells that need absolute Unix paths on the device.
- **Endpoint security and unexplained kills.** Endpoint security on this machine has killed long shells and agents before. If the Bash tool breaks ("bash.exe not found"), a shell or an agent vanishes without explanation, or a Gradle run is killed with no error of its own: stop, report to the orchestrator, check the endpoint-security log, and do not work around it. Never re-run a half-finished writer pass or a half-finished mutation on a guess: a mutation left in place is recovered by the protocol in U-067's plan (compare the file's hash with the saved blob, restore from the pristine copy; if that is lost, `git cat-file --filters --path=<path> <blob>`; never `git checkout`, which would discard the fix).
- **A step-by-step implementation log from the start**, written after every step, so an interrupted session can resume from it (sprint-017 retro, recommendation 5).
- **Regenerating the wrapper drops the Windows block.** Re-apply it before the next Gradle call; the signal of a loss is "Unable to establish loopback connection".
- **Clean before measuring coverage after an AGP or Kotlin change** (U-060 found a stale Kotlin class directory that would have satisfied the class-root guard on stale classes). Do not explain a coverage shift by "JaCoCo counting" without proof: U-060's first such explanation was wrong, and QA found the real cause (AGP 9's unit-test manifest drops the app's own components) by rebuilding the old toolchain.
- **Evidence hygiene.** Text evidence only: no screenshots, no account names, no host names, no user-profile paths, no e-mail addresses; redact before saving (sprint-017 retro, item 4, and its security-review finding). Small text files are committed; raw logs and large reports that carry such data stay in the session scratch folder and are never written into a repository file by absolute path.
- **A shared emulator is left as found.** Turn the third-party-integration setting off before the device run (sprint-017: it was left on and started a real backup), restore every app setting touched, shut the emulator down.
- **Network.** A toolchain raise downloads a Gradle distribution, plugins and libraries from the usual repositories (Gradle services, Google Maven, Maven Central) through the build itself; that is the build's normal path and is allowed. Nothing is downloaded by hand from anywhere else; checksums and verification metadata are handled as design D5 and AC-17 say. Reading a vendor page or a published checksum is a read, not a build input; Robolectric's `android-all` jars are fetched by Robolectric's own resolver at test time, outside Gradle's verification (recorded, design D5).
