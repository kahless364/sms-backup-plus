## Open questions the analysis must still settle by experiment

1. **Can `:mail:common` + `:mail:protocols:imap` be built outside the upstream tree at all?** They need `:core:common`, `:legacy:logging`, `:feature:account:api`, `:feature:mail:folder:api` (+ `:core:architecture:api`, `:feature:mail:account:api`), which are KMP modules built by upstream convention plugins (`build-plugin/`, isolated projects, type-safe accessors, JDK 21+ check, Kotlin 2.4.21, AGP 9.5.1, Gradle 9.6/9.7). A trial is needed to learn the smallest copy that compiles under the app's Gradle 9.x / AGP 9.x / JDK 25 build, and how many source edits it takes (e.g. replacing the KMP modules with a handful of copied classes: `MessagingException`, `Flag`, `HostNameUtils`, `CertificateBlocklist`, `Log`, `AccountId`, `FolderPathDelimiter`).
2. **Effective minSdk.** Upstream KMP Android targets declare minSdk 24; the two mail modules are JVM-only. Does an Android app with minSdk 23 resolve the `jvm` or the `android` variant of the KMP dependencies when consuming them (composite build vs vendored sources), and does manifest merging then fail? Does anything in the JVM code paths actually need API 24 or core-library desugaring (e.g. `java.time`; the Android API level of `javax.net.ssl.SNIHostName` was not looked up in this session — recollection only: API 24 — relevant if `DefaultTrustedSocketFactory` is copied)? The published TMC artifacts declare minSdk 23.
3. **Kotlin metadata compatibility.** Upstream compiles with Kotlin 2.4.21 and the published TMC artifacts with 2.4.20; the app is on KGP 2.3.21 with a recorded Hilt/Kotlin-2.4 metadata blocker. If sources are vendored they are compiled by the app's own Kotlin (does 2.3.21 accept the upstream sources, which use e.g. multi-dollar string interpolation `$$"$Forwarded"` in `ImapUtility.kt` L134?). If binaries are consumed, can the app's compiler and Hilt/KSP read them?
4. **Coroutines version.** `suspend fun fetch` plus bundles expect kotlinx-coroutines 1.11.0; the app has 1.7.3. Does REQ-MODERNIZATION-016's target version satisfy it, and does a `runBlocking` Kotlin shim around `fetch` behave correctly on the app's worker threads?
5. **APPEND internal date.** Upstream does not send it. Options to test: re-apply the fork patch to a vendored `RealImapFolder` (it is `internal`), or accept server-assigned internal dates. Needs a GreenMail and a live-Gmail check of what the restore path and Gmail's date ordering do without it (AC-B4/B5 list internal date as a compared field).
6. **UID SEARCH by `X-smssync-datatype` header.** No public API. Test whether (a) patching a vendored copy to expose a raw search, (b) calling Kotlin-`internal` members from Java/Kotlin (name-mangled), or (c) same-package access tricks are workable and maintainable; each needs a compile-and-run proof.
7. **Headers-only fetch.** Upstream `ENVELOPE` fetch uses a fixed header list without `X-smssync-*` and there is no `Item.DATE`. Measure the cost of using full `BODY` fetch for the "sort newest N" path, or patch the header list.
8. **Byte-level MIME equality (AC-B4).** Build the same SMS/MMS/call-log messages with the vendored stack and with upstream `MimeMessage`/`MimeMessageHelper`/`TextBody`/`Base64OutputStream` (mime4j 0.8.15) and diff: `Content-Type` formatting (folding, `charset` parameter), address header folding via `AddressHeaderBuilder`, subject encoding via `MimeHeaderEncoder`, boundary generation, base64 line length, `Message-ID` generation.
9. **Restore compatibility.** Parse fixture messages written by the old stack with the upstream parser (header decoding changed in `6e3a55db2b`) and compare restored content.
10. **SNI / hostname behaviour on the app's device matrix.** Upstream's SNI guard has no blank-host case and its hostname verifier is httpclient5's; run the equivalent of `DefaultTrustedSocketFactorySniTest` (DNS name, IPv4, IPv6, blank) and a mismatched-hostname test against whichever factory is kept (the app's own vs a copied upstream one). Check `SNIHostName`/`SSLParameters.setServerNames` availability at API 23.
11. **Logging bootstrap.** Confirm what happens when `Log.logger` is unset, and what minimal `Logger` implementation satisfies it (requires the MPL-2.0 `logging:core` artifact, or a local replacement of the facade in vendored sources).
12. **Dependency verification and size.** Number of new entries required in `gradle/verification-metadata.xml` (okio, moshi, httpclient5 + httpcore5 + httpcore5-h2 + slf4j-api, koin-core, kotlinx-datetime, kotlinx-serialization-json, kotlinx-collections-immutable, TMC outcome/logging, newer mime4j/commons-io); release-APK size and method-count delta after R8 — only `assembleRelease` can answer (REQ question 8).
13. **Licence position on MPL-2.0 transitive artifacts** (`components.core:outcome`, `components.core.logging:core`) and the unread licences of `httpcore5`, `httpcore5-h2`, `slf4j-api`: needs a decision and, for the latter three, a POM read (AC-A3 requires an SPDX id per transitive dependency).
14. **GreenMail compatibility.** Do the existing `BackupImapStoreDelegateIntegrationTest` cases pass against upstream's connection sequence (CAPABILITY, optional `COMPRESS=DEFLATE`, `ID`, `ENABLE UTF8=ACCEPT`, `NAMESPACE`), and does `SASL-IR` being mandatory for XOAUTH2/OAUTHBEARER (`RealImapConnection.kt` L316-317) matter for the test server?
15. **Upstream intent.** Ask the maintainers (issue or Matrix) whether the IMAP/MIME code is planned to move into `thunderbird-mobile-components` as a published artifact, and whether a PR adding APPEND-with-date and a header-search API would be accepted — no written statement was found (9.9).
