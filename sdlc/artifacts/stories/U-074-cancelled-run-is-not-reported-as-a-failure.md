# U-074: Make a Cancelled Backup or Restore End as Cancelled, Not as an Error Line and a Failure Result, by Deciding on the State of the Running Coroutine's Job, and Stop the Cancel Collector Warning on Every Normal Finish

## Story
As the owner of this private, unpublished SMS Backup+ build (its only user, who reads the log tag `SMSBackup+` on device checks and treats an error-priority line as a failure),
I want a backup or restore run that I cancel, that a newer enqueue replaces, or that the system stops, to end as a cancelled run, with one information line and no error line and no failure result, while a genuine failure is still logged and reported exactly as today,
So that the log tells the truth about why a run stopped, the device checks of the next stories stop reading a false failure signature, and the worker's own report no longer depends on a WorkManager library detail (the library's dropping the result of a stopped worker) that the runtime-library story is about to change.

Source: bug BUG-024 (`sdlc/artifacts/stories/BUG-024-cancelled-backup-or-restore-reported-as-failure.md`, status ready, severity low, priority medium), fixed by the approach the Solution Architect ruled in the bug's `## Suggested Approach` (rulings 1 to 6, section 2 "The exact shape of the fix", section 3 "Testability", section 4 "Scope Concerns") and by the orchestrator's ruling on order (this story is built after story U-070 and before story U-071). There is no REQ-* source; the contract sentence the fix makes true is in CNTR-MODERNIZATION-004, Error Handling, "Cancellation is terminal, not failure" (`sdlc/artifacts/design/contracts/CNTR-MODERNIZATION-004-backup-scheduler.md:287`). The rulings are binding and are not re-decided here; the criteria below carry them.

**What the fix is, in one paragraph.** A cancelled run is identified by the state of the coroutine job that runs the worker, not by the type of the exception that was caught. One new internal function, `rethrowIfCancelled`, in a new file `app/src/main/java/com/zegoggles/smssync/service/WorkerCancellation.kt`, is the first statement of five existing broad catches (`BackupWorker.kt` in `doWork`; `RestoreWorker.kt` in `doWork`, `executeRestore`, `runImapRestoreLoop` and `executeRestoreWithValues`) and of one catch in `WorkManagerCancelCollector.kt`. If the job is cancelled, the run ends by throwing (a `CancellationException` is rethrown as it is; any other exception is logged once at warning level and the job's `CancellationException` is thrown), nothing is returned, and `doWork` writes one information line. If the job is active, the function returns and the catch handles the exception exactly as today, even when it is a `CancellationException`. Nothing else in the catches, the `finally` blocks, the typed catches or the signatures changes.

**Not in this story** (each ruled or recorded; none is an acceptance criterion):
- The conversation-thread refresh on a cancelled IMAP restore (`updateAllThreadsIfAnySmsRestored`). It is skipped before and after this fix. Ruled out (bug SC-1); whether it should run is a product-owner item (PO-1) recorded with BUG-018.
- Any contract or design edit. The change record that states what the worker does on cancellation (CNTR-MODERNIZATION-004 v4, non-breaking) is raised by the orchestrator after this story and before story U-073 is planned (hand-over item H-1).
- The WorkManager-level test of the work state after a cancel and after a REPLACE. It belongs to story U-073, increment W (hand-over item H-2).
- A device check. No device check is required. The optional one on the Android 16 emulator (the bug's PO-2) is the product owner's item and, if allowed, is run by the orchestrator only.
- `MainViewModel.kt`, the sync-button path (`StatusPreference.java`), `WorkManagerScheduler.kt`, the typed catches, the vendored library, dependencies and build files.

### Library facts the approach rests on (read by the architect, not run; full table L1 to L16 in the bug's Suggested Approach section 1)

- WorkManager 2.9.1: `WorkerWrapper.interrupt` resolves the wrapper before it cancels the worker's future; `CancelWorkRunnable` sets CANCELLED before it stops the work; a REPLACE cancels then deletes; a system stop gives ENQUEUED (rescheduled). A `CancellationException` thrown while the worker is not stopped is recorded as FAILED. The result of a stopped worker is not applied.
- WorkManager 2.12.0: a stopped worker's wrapper continuation is cancelled with a `WorkerStoppedException` before the worker's job is cancelled, giving `Resolution.Stopped`; any other `CancellationException` out of the worker gives `Resolution.Failed` ("self-cancelled"), reached only when the job is active. So a rethrow keyed on the job's state meets the library in every case.
- Coroutines: `CoroutineContext.isActive` and `ensureActive()` exist in 1.7.3 and 1.11.0; `runBlocking` rethrows a `CancellationException` (1.11.0 read; 1.7.3 not).
- Hierarchy: `kotlinx.coroutines.CancellationException` is `java.util.concurrent.CancellationException`, an `IllegalStateException`; that is why the restore catches written for "possible memory" take it.
